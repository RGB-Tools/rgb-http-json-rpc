# protocol improvement specification

This document specifies changes to the RGB HTTP JSON-RPC transport protocol.

Concerns that belong to the client (wallet/library) rather than the protocol or
proxy are intentionally left out of the main body. Two client-facing concerns
that are nonetheless needed for interoperability are documented as appendices:
the end-to-end payload encryption layer (Appendix A, which the proxy stores but
never inspects) and the recommended invoice interaction (Appendix B, which the
proxy never sees). The adaptive proof of work (Appendix C) is instead part of
the protocol, since the proxy verifies it, but its details are documented as
an appendix for readability.

## 1 overview

Four improvements are proposed:
1. sender-side proxy
    - a new proxy endpoint where the sender expects the recipients' signed ACK
    - sender posts its transport endpoint to the recipient proxy when posting
      the consignment
    - sender posts the transfer ID, recipient pubkey and signed TX to its
      proxy of choice
    - sender proxy receives recipients' ACK, verifies signature and expiration,
      then releases the signed TX
    - sender has control over ACK data (retention, tampering)
    - recipients can broadcast the TXs without waiting for the sender
2. signed ACK messages
    - recipients include a pubkey in the invoice
    - recipients sign ACK messages with the corresponding secret key
    - sender proxy verifies ACK signature
3. optionally encrypted consignment and media, and encrypted signed TX
    - all data is encrypted by default
    - recipients can specify if consignment and media should be encrypted
    - sender posts its pubkey to the recipient proxy when posting the
      consignment
    - both sender and recipient derive the same shared secret from combining
      their respective key pairs and use it to derive a symmetric key that is
      used for encryption
    - encryption is stream oriented so streaming upload/download and data
      processing can also be supported
    - the encryption itself is end-to-end and opaque to the proxy (Appendix A)
4. invoice reuse
    - recipients reserve an invoice on their proxy, with a quota of transfers
      it can receive (a single-use invoice has a quota of 1)
    - each transfer is identified by a transfer ID, derived from the invoice
      and a fresh sender key
    - both addresses (witness receives) and blinded UTXOs (blind receives) can
      be reused
    - the witness seal blinding is derived from both parties' keys instead of
      being chosen by the sender
    - public invoices are protected against spam via an adaptive proof of work
      (Appendix C)

## 2 current architecture

### 2.1 proxy protocol

Relevant endpoints:

| method | caller | target proxy | purpose |
|--------|--------|--------|---------|
| `ack.get` | sender | recipient | get ACK/NACK status |
| `ack.post` | recipient | recipient | post ACK/NACK boolean |
| `consignment.get` | recipient | recipient | fetch consignment + metadata |
| `consignment.post` | sender | recipient | upload consignment + metadata |
| `media.get` | recipient | recipient | fetch media attachment |
| `media.post` | sender | recipient | upload media attachment |
| `server.info` | any | recipient | expose server info |

### 2.2 current transfer flow

The following diagram depicts the current typical transfer flow.

```
Recipient                          Sender
    |                                |
    |-- create invoice including --->|
    |   the recipient proxy URL      |
    |                                |
    |    post consignment to proxy --|
    |                                |
    |-- get consignment and media    |
    |                                |
    |-- post ACK to proxy            |
    |   (no signature)               |
    |                                |
    |           get ACK from proxy --|
    |                                |
    |                 broadcast TX --|
    |                                |
    |--   wait for confirmations   --|
```

### 2.3 limitations

- no ACK authentication: ACK is a plain `bool`, so a malicious proxy or third
  party could tamper with ACK replies
- no ACK proof: the sender has no reliable proof that the recipient accepted
- misplaced ACK control: ACK is posted to the recipient's proxy, so the sender
  has no control over data retention nor tampering
- mandatory sender interaction: only the sender can broadcast the TX after
  receiving the ACK, the recipient must wait
- privacy leak due to cleartext data (consignment, media and TX)
- no data retention policy: stored data currently has no expiration, so a proxy
  either keeps it forever or has it wiped manually
- no address reuse: the recipient ID of a witness receive is derived from the
  address alone, so reusing an address would make recipient IDs collide
- single-use invoices: each invoice maps to a single recipient ID, so it can
  only be used for a single transfer
- sender-chosen witness blinding: the sender chooses the blinding factor of
  the recipient's witness seal, with no incentive to choose a good one, and
  the recipient cannot enforce its quality

## 3 design decisions

### 3.1 sender proxy

The sender will use a proxy server of his choice for the operations the
recipient proxy offers insufficient guarantees for.

The sender needs to provide the transport endpoint of his choice to the
recipient:
1. sender includes their transport endpoint when posting the consignment to the
   recipient's proxy
2. recipient's proxy stores and returns it alongside the consignment response
3. the recipient uses this transport endpoint to post its ACK

### 3.2 ACK authentication

The sender posts the data required for ACK signature verification to its proxy
before posting the consignment to the recipient proxy.

The recipient gets the consignment and related data and uses it to post a
signed ACK to the sender proxy.

When an ACK is posted, the sender proxy verifies the signature using the pubkey
associated to the transfer ID.

When the sender retrieves the ACK from its proxy it also gets the associated
signature and stores it as proof of authentic acknowledgement.

### 3.3 TX release

The sender posts the signed TX along with the data required for ACK signature
verification to its proxy.

When the recipient posts an ACK to the sender's proxy, if the signature is
valid and the associated expiration is not in the past, the proxy returns the
signed TX.

### 3.4 reusable invoices

Allowing invoice reuse requires the per-transfer identifier to be unique even
when the beneficiary is the same. Uniqueness is also needed at the RGB level,
not only on the proxy: with a reused beneficiary one output could otherwise be
credited under two different identifiers.

The recipient reserves an invoice (rather than a recipient ID) on its proxy,
with a quota: the maximum number of transfers the invoice can receive. A
single-use invoice is simply an invoice with a quota of 1, so a single
mechanism covers both cases and the invoice format does not change.

The recipient is identified by the invoice, while each transfer is identified
by a transfer ID, derived from the invoice and a fresh key chosen by the sender
for each operation. Senders sign their uploads with that key, so no third party
can take over a transfer ID.

For witness receives, the seal blinding factor is derived from both parties'
keys, so it is unique per transfer, known only to the two parties and not
chosen by the sender. For blind receives, the blinding factor is already chosen
by the recipient and embedded in the invoice, so it's not unique per transfer.

An invoice can be shared publicly, in which case anyone can post fake
transfers and fill its quota. The optional proxy authentication does not help
here, since it protects invoice reservations while transfers must be open to
any sender. Recipients can delete unwanted transfers to restore the quota and
an adaptive proof of work (Appendix C) makes spam expensive while the proxy is
under attack, without affecting honest senders otherwise.

### 3.5 encrypted data

The consignment and the media attachments are optionally encrypted (governed by
the recipient's encryption preference, see Appendix B) and the signed TX is
always encrypted.

The encryption will be stream-oriented to support streaming transfer and
validation of data, which is especially relevant for big files.

The encryption symmetric key will be independently derived by each party from
their respective key pairs, which they exchanged. The full scheme is defined in
Appendix A; it is end-to-end between the two parties and opaque to the proxy,
which only ever stores and returns the resulting bytes.

### 3.6 backward compatibility

Backward compatibility is not maintained and clients will need to be updated in
order to successfully interact with updated proxy servers.

An updated client will refuse to process or immediately fail an operation if:
- the recipient pubkey is not present in the invoice
- the expiration is not present in the invoice
- the proxy server runs a protocol version lower than the required one (via
  `server.info` → `protocol_version`, already exposed)

Proxy server endpoints are incompatible with the old ones and return errors if
API calls do not respect the new requirements.

Avoiding backward compatibility allows this update to remain much simpler, so
it is preferred to avoid unnecessary complexity both in the proxy and clients
that call its API endpoints.

It should be possible to add backward compatibility at a later time, if there
are strong reasons to do so, although this is not planned nor expected to
happen.

## 4 specification

The following definitions are used throughout the specification:
- invoice: the recipient's request to receive (see Appendix B); an invoice is
  reserved on the recipient proxy via `invoice.prepare` and can receive up to a
  quota of transfers
- invoice ID: the identifier of an invoice on the proxy, computed as the
  hex-encoded SHA-256 of the concatenation, encoded as UTF-8 bytes, of the
  literal string `rgb-proxy-server/invoice/v1`, the beneficiary string (see
  below) and the invoice pubkey, with no separators
- beneficiary string: the canonical string form of the invoice beneficiary,
  i.e. the chain network prefix (e.g. `bc`, `tb4`, `bcrt`), a `:`, then either
  `utxob:` followed by the Baid64-encoded concealed seal (blind receives) or
  `wvout:` followed by the Baid64-encoded pay-to-vout payload (witness
  receives), in both cases including the `-` chunk separators, followed, for a
  witness beneficiary that includes an internal key, by `+` and the
  hex-encoded internal pubkey; implementations must re-encode the parsed
  beneficiary in this form, regardless of how it appears in the received
  invoice (e.g. without separators), and must never use the plain bitcoin
  address
- invoice pubkey: the recipient pubkey included in the invoice (`pk` query
  parameter, see Appendix B); it is the recipient pubkey for all the transfers
  to the invoice and a fresh one is used for each invoice (see A.10)
- transfer: a single transfer to an invoice; it is created on the recipient
  proxy by a successful `consignment.post` call
- transfer ID: the identifier of a transfer, computed as the hex-encoded
  SHA-256 of the concatenation, encoded as UTF-8 bytes, of the literal string
  `rgb-proxy-server/transfer/v1`, the invoice ID and the sender pubkey
  (`sender_pk`), with no separators
- quota: the maximum number of transfers an invoice can receive (1 for a
  single-use invoice)

Notes:
- the invoice pubkey makes the invoice ID impossible to compute without knowing
  the invoice, even when the beneficiary is known (e.g. a reused address that
  already appears on-chain), so no third party can reserve it in advance
- the sender uses a fresh key pair for each operation, so each operation yields
  a different transfer ID for the same invoice; a single operation can
  therefore include at most one transfer per invoice
- the witness seal blinding factor is derived from the key pairs of the two
  parties (see Appendix A.11), so each transfer uses a different one; the blind
  seal blinding factor is chosen by the recipient and embedded in the invoice,
  so all transfers to a blind invoice use the same seal
- the beneficiary string must be exactly the canonical one, since any other
  form (e.g. without the `-` chunk separators, as some invoice encodings
  display it, or a plain bitcoin address) yields different invoice and
  transfer IDs, breaking interoperability; for example, removing the
  separators from the blind beneficiary string in the example below would
  yield the invoice ID
  `a77acac648921fe286bc2dd954cbec04972838c13b0e3571e97c9b165c23fcd8`

### 4.1 keys and signatures

Every party involved in an operation holds an Ed25519 key pair, made of a
secret key and the corresponding public key (pubkey). The recipient pubkey is
shared via the invoice (see Appendix B) and echoed in the relevant proxy calls
via the `recipient_pk` field. The sender pubkey is communicated to the
recipient via the relevant proxy calls via the `sender_pk` field.

Secret keys are never transmitted, so every `pk` field name or suffix (and the
`pk` invoice query parameter) always refers to a pubkey, consistently with the
common pk/sk naming convention. The pubkeys optionally configured on a proxy to
authenticate `invoice.prepare` and `ack.prepare` calls (authentication pubkeys)
are keys with a different purpose, belonging to the proxy operator(s) or their
authorized users rather than to the parties of an operation.

Pubkeys and signatures are transmitted as lowercase hex strings, consistent
with the protocol's existing use of hex for identifiers and hashes.

Several endpoints are authenticated by, or gate on, a signature. In every case
the scheme is identical:
- a canonical message is defined per endpoint as a concatenation, encoded as
  UTF-8 bytes, of a fixed sequence of fields, with no separators
- the signed value is the 32-byte SHA-256 digest of that concatenation
- the digest is signed with Ed25519 using the signer's secret key
- the proxy verifies by reconstructing the concatenation from the fields it
  received and/or stored, computing its SHA-256 digest and checking the Ed25519
  signature against the relevant pubkey

Although every endpoint's signature check follows this same scheme, the
signatures themselves prove different things and are reported with distinct
error codes rather than a single generic one, so a caller can tell which check
failed:
- `invalid proxy auth signature`: optional proxy-level authentication
- `invalid endpoint auth signature`: mandatory operation ownership proof
- `invalid content signature`: mandatory content signature

### 4.2 payload encryption on the wire

All data may be transmitted encrypted. Encryption is end-to-end between the two
parties and the proxy never decrypts, so from the proxy's point of view:
- file blobs are opaque byte strings, the proxy stores and returns them as-is
  and must not attempt to interpret, validate or relate them to any hash it
  also stores
- hashes are opaque metadata: they are the hashes of the *plaintext* and
  therefore must not be validated against the hash of the (possibly encrypted)
  uploaded bytes
- the only hash the proxy relates to the uploaded bytes is the one it computes
  itself over them (the hex-encoded SHA-256 of the uploaded bytes, referred to
  as `blob_hash`), which is used to verify the sender signature on
  `consignment.post` and `media.post` and is never received from the caller
- media is addressed per transfer by an opaque `media_id` rather than by a
  content digest, which the proxy must not try to relate to the stored bytes

### 4.3 ACK + signed TX

The ACK message is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of the `transfer_id` (string), the ACK value (the literal string `true`
or `false`) and the consignment hash (the hex-encoded SHA-256 of the plaintext
consignment). The consignment hash used here is the same value the sender
registers per transfer via `ack.prepare` and that the recipient receives via
`consignment.get`, so both parties produce the same message.

The message is signed with the recipient's secret key corresponding to the
invoice pubkey (see 4.1 for the signature primitive).

To verify an ACK signature, the sender proxy reconstructs the ACK message using
the `transfer_id` and consignment hash registered via `ack.prepare` and the ACK
value received via `ack.post`, computes its SHA-256 hash and verifies the
signature against the recipient pubkey registered for that transfer ID.

Notes:
- the ACK message contains the consignment hash, which ensures the client has
  at least downloaded the correct consignment and means the sender needs to
  save the original data in order to be able to produce it in case the ACK
  needs to be later challenged
- the ACK signature verification is carried out on the sender proxy, as it's a
  required step to release the signed TX
- the message is not encrypted since the verification happens on the proxy,
  which would need knowledge of the encryption scheme to decrypt the message,
  which would expose both parties to a bigger privacy risk (data leak) than the
  ACK message leak alone
- the sender should independently re-verify the ACK signature after getting
  it from the sender proxy but, at that point, the signed TX would have already
  been released by the proxy so the only thing that can be done is to try and
  double-spend it (see 6.3 for how to handle an invalid one)
- the recipient should verify the TX before broadcasting, although the sender
  cannot be prevented from broadcasting it on the next refresh

### 4.4 proxy endpoints

General notes:
- the "cannot change", "invalid" and "missing" errors will be single errors
  (instead of per-field ones) and include the list of fields that failed
  validation
- the error `data`, when present, contains the list of failing fields
  (`fields`) or, for the "invalid proof of work" error, the current difficulty
  (`pow_difficulty`)
- the fields are parameter names: for values nested in a parameter (entries of
  `transfer_data`, items of `transfer_ids`) the inner name is used (e.g.
  `recipient_pk`, `transfer_id`), while `file` refers to the uploaded file
- when more than one error is possible (e.g. both "invalid" and "missing"), the
  missing error is returned first and only all requested data is present
  "invalid" is returned
- each request carries a single call: JSON-RPC batches (requests made of an
  array of calls) are refused with the JSON-RPC "invalid request" error
  (`-32600`), since they would multiply the cost of a request beyond what the
  limits of each call (max transfers, max file size, ...) allow; this has
  nothing to do with the `batch` parameter, which flags an operation with
  several transfers and is supported
- for the same reason the proxy bounds the size of the JSON body of a request
  to about `max_transfers` IDs (plus some overhead for the other fields) and
  refuses bigger ones with the same error, aborting them while they're being
  received; the error is the generic one because the method is not known yet
  and any method can be the target (a "signed TX too large" error would be
  misleading, as no signed TX travels in the JSON body)
- clients must therefore send one call per request and disable the automatic
  batching some JSON-RPC libraries do; a JSON-RPC batch fails as a whole, with
  a single error and no per-call results

#### 4.4.1 extended endpoint: `server.info`

Expose the current time, the configured maximum allowed expiration for invoice
(`invoice.prepare`) and ACK (`ack.prepare`) reservations, the configured
maximum allowed invoice quota, the configured maximum proof of work difficulty,
the configured retention grace and the configured size and count limits
(maximum file size, maximum signed TX size, maximum transfers and maximum
media).

The current time can be used by clients to compute the clock skew with respect
to the proxy server.

The max expiration is the number of seconds in the future that an expiration is
allowed to be set to (e.g. 2592000 for 30 days max).

The max quota is the maximum number of transfers an invoice can be reserved for
(see `invoice.prepare`).

The max proof of work difficulty is the maximum difficulty the proxy can
require on `consignment.post`, with `0` meaning that proof of work is disabled
(see Appendix C).

The retention grace is the number of seconds the proxy guarantees to keep data
awaiting retrieval after its expiration, and after which it can delete it, with
`0` meaning that no grace is granted: the data of pending transfers (neither
retrieved nor deleted by the recipient) after the invoice expiration and the
operation data (ACK values, signatures and released signed TXs) after the
operation expiration (see 4.6).

The max file size is the maximum size, in bytes, of a file uploaded via
`consignment.post` or `media.post` (see 4.4.15). It does not apply to the file
of `ack.prepare`, whose maximum size is derived from the max transfers and the
max signed TX size (see 4.4.4); it is not advertised separately, as clients can
compute it.

The max signed TX size is the maximum size of each signed TX in `ack.prepare`,
measured as the length of the base64 signed TX string (see 4.4.4).

The max transfers is the maximum number of transfers an `ack.prepare` call can
include (see 4.4.4). It also bounds the number of IDs in `invoice.check`,
`ack.clean` and `ack.get` calls (see 4.4.2, 4.4.9 and 4.4.11), and the size of
the JSON body of any request (see 4.4 general notes).

The max media is the maximum number of media attachments a transfer can have
(see 4.4.7).

Exposing these limits allows clients to know in advance what the proxy accepts,
instead of finding out by failing.

New response fields:
- `current_time`: string (unix absolute timestamp, seconds, UTC)
- `max_expiry_secs`: string (seconds)
- `max_quota`: string (number of transfers)
- `max_pow_difficulty`: string (number of leading zero bits)
- `retention_grace_secs`: string (seconds)
- `max_file_size`: string (bytes)
- `max_signed_tx_size`: string (length of the base64 string)
- `max_transfers`: string (number of transfers)
- `max_media`: string (number of media attachments per transfer)

`uptime` stays a JSON number, as in previous versions: `server.info` keeps the
shape of its pre-v1.0 fields (`protocol_version`, `version`, `uptime`) so that
any client can parse it and detect the protocol version, while the new fields
are strings.

#### 4.4.2 new endpoint: `invoice.check`

Allow a wallet to ask a proxy whether one or more invoices can accept
transfers.

The proxy reports an invoice (status) in three different ways:
- `unknown`: the invoice ID is not known to the proxy (it has not been
  reserved, or its data has been deleted)
- `available`: the invoice ID has been reserved via `invoice.prepare` and can
  still accept transfers (its quota is not full)
- `full`: the invoice ID has been reserved via `invoice.prepare` and its quota
  is full

Alongside each status, the proxy reports the proof of work difficulty currently
required to create a transfer for the invoice (see Appendix C).

Transfer IDs reserved with `ack.prepare` or used with `ack.post` are not
considered, as senders just call `ack.prepare` and recipients just call
`ack.post` and can deduce the transfer ID status from the response.

Senders initiating an operation should query all the relevant recipient
transport endpoints, for each recipient. Specifically, check for each invoice
on all transport endpoints it lists, typically stopping at the first one that
returns `available`.

Parameters:
- `invoice_ids`: array of invoice_id(string)

Response on success:
- `result`: a map from invoice ID to an object holding:
    - `status`: string (see above)
    - `pow_difficulty`: string (number of leading zero bits)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- invalid (invoice ID)
- missing (invoice_ids)
- too many items

Notes:
- the check is read-only and has no side effects: it does not reserve an
  invoice, so an `available` result is not a guarantee that a later
  `consignment.post` will succeed (concurrent senders could fill the quota and
  the proof of work difficulty could rise in between); it is a best-effort
  early-detection aid, except when invoices are shared privately
- `available` and `full` reflect the invoice ID presence regardless of the
  invoice expiration, which the sender knows from the invoice itself; an
  invoice ID is removed by wiping proxy data or by the retention policy once
  the expiration and, if it still has pending transfers, the retention grace
  have passed (see 4.6)
- the endpoint needs no authentication (it exposes only a tri-state and the
  current difficulty about an invoice ID, which cannot be computed without
  knowing the invoice)
- the proxy should refuse a request with more than the configured max invoice
  IDs, advertised as `max_transfers` via `server.info` (e.g. 1000), lest the
  unauthenticated endpoint would remain vulnerable to DoS attacks via huge
  numbers of lookups and huge responses; this is enough for legitimate use,
  since a sender checks the invoices of a single operation, which has at most
  `max_transfers` transfers
- this is also how a sender learns whether an invoice can be used for more than
  one transfer, since nothing in the invoice itself signals it
- this is especially useful in a multisig setup, where sender cosigners need to
  coordinate before actually finalizing the operation (when `consignment.post`
  or `ack.prepare` could be rejected)

#### 4.4.3 new endpoint: `invoice.prepare`

Allow the recipient to POST the invoice ID required by the recipient proxy to
handle calls to the `consignment.post` and `media.post` endpoints, thus
reserving the invoice ID before including the transport endpoints in the
invoice. A reservation also carries the expiration that governs how long the
proxy retains the recipient's data (see 4.6), the quota of transfers the
invoice can receive and the invoice pubkey, which authenticates the recipient
on `transfer.list`, `transfer.retrieved` and `transfer.delete`.

The proxy server can optionally be started with a list of pubkeys that will be
used to authenticate calls to this endpoint: when configured, the caller must
sign the message and the proxy refuses unauthenticated calls. This allows an
operator, or group of, to run a recipient proxy that avoids unwanted invoice
reservations (DoS).
The message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of `invoice_id`, `expires_at`, `recipient_pk` and the quota (the `quota`
value, or `1` if the parameter is omitted), with no separators.

Parameters:
- `invoice_id`: string
- `expires_at`: string (unix absolute timestamp, seconds, UTC)
- `recipient_pk`: string (the invoice pubkey)
- `quota` (optional): string (number of transfers, defaults to `1`)
- `signature` (optional): string (required only if the proxy is started with
  authentication pubkeys)

Invoice IDs are kept unique on the proxy: an invoice ID can be reserved at most
once, and the consignment and media can only exist for a transfer to a reserved
invoice, lest they would lack a data retention policy (expiration) or could
lead to a DoS even on authenticated instances.

Response on success:
- `result`: `true` if the invoice ID is newly reserved
- `result`: `false` if the same invoice ID was already reserved with the same
  `expiration`, `recipient_pk` and quota (idempotent)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- cannot change (expiration | recipient_pk | quota): the invoice ID is already reserved
  with different values
- invalid (invoice ID | expiration | recipient_pk | quota)
- missing (invoice ID | expiration | recipient_pk)
- invalid proxy auth signature

Notes:
- the reservation, the transfers and their consignment and media for an
  invoice ID share the reserved expiration and can be deleted once it passes,
  except for pending transfers (neither retrieved nor deleted by the
  recipient), which are kept until the retention grace has passed (see 4.6); the
  reservation cannot be removed before its expiration
- `expires_at` can be invalid both because it's in the past and because it's
  too far in the future (exceeds the configured `max_expiry_secs`)
- `quota` can be invalid both because it's lower than 1 and because it exceeds
  the configured `max_quota`; it's rejected rather than silently clamped, so
  the recipient always knows the exact quota in effect
- the proxy cannot verify that `recipient_pk` matches the invoice ID (it
  doesn't know the beneficiary) nor does it need to: whoever reserves the
  invoice ID first owns the reservation, which is why the recipient must
  reserve it before sharing the invoice (see Appendix B)
- the recipient must reserve the invoice on all the transport endpoints listed
  in the invoice with the same expiration and `recipient_pk`, which must match
  the invoice one (see Appendix B), and the same quota
- each proxy is independent and cannot know whether, nor with which data, the
  same invoice ID is reserved on other proxies: expiration, quota and transfer
  ID uniqueness are enforced per proxy, so an invoice listing several
  transport endpoints can receive up to the sum of their quotas; keeping the
  reservations consistent is the recipient's responsibility, while senders
  never rely on the data registered on the recipient proxy (they use the
  pubkey and expiration from the invoice)
- no replay attack protection for signatures is included as the proxy owner(s)
  are trusted by (or coincide with) the owners of the secret key(s)

#### 4.4.4 new endpoint: `ack.prepare`

Allow the sender to POST the transfer data required by the sender proxy to
handle calls to the `ack.post` endpoint.

The `transfer_data` parameter is a map from the transfer ID to an object
holding the recipient pubkey (the invoice pubkey) and the consignment hash. This
allows the sender to provide all the required transfer data, including batch
transfers. The consignment hash is needed by the proxy to reconstruct and
verify the ACK message.

The signed TXs travel in the uploaded file, not in the JSON parameters, so that
the size of the JSON body of a request can be bounded tightly (see 4.4 general
notes): the file is a JSON object mapping each transfer ID to its base64
encoded signed TX, with exactly the transfer IDs of `transfer_data`. As for the
other uploads, the `file_size` parameter declares its size (see 4.4.15).

An operation has a single plaintext signed TX (one bitcoin transaction, even
for a batch with multiple recipients), but each recipient uses different
encryption keys, so there is one encrypted `signed_tx` per transfer, in the
file. The top-level `signed_tx_hash` is the hex-encoded SHA-256 of
the plaintext signed TX; since the plaintext is the same for every recipient,
the hash is shared. The proxy returns the recipient's own `signed_tx` together
with `signed_tx_hash` so the recipient can derive the decryption nonce (see
Appendix A.5) and verify the decrypted TX.

The `sender_pk` parameter contains the pubkey of the caller (sender).

The proxy server can optionally be started with a list of pubkeys that will be
used to authenticate calls to this endpoint: when configured, the caller must
sign the message and the proxy refuses unauthenticated calls. This allows an
operator, or group of, to run a sender proxy that avoids unwanted transfer ID
reservations (DoS).
The message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of `sender_pk`, `expires_at`, `signed_tx_hash` and, for each sorted
transfer, `transfer_id` followed by `recipient_pk` followed by
`consignment_hash`, with no separators. Transfers are sorted lexicographically
by transfer ID. The encrypted `signed_tx` is bound to the message through
`signed_tx_hash` and is not itself part of the signed bytes: for this reason the
proxy verifies the signature before reading the file, so that a caller that
isn't allowed doesn't make the proxy read it.

Parameters:
- `transfer_data`: {transfer_id(string): (recipient_pk(string), consignment_hash(string)), ...}
- `expires_at`: string (unix absolute timestamp, seconds, UTC)
- `signed_tx_hash`: string
- `sender_pk`: string
- `file_size`: string (bytes)
- `signature` (optional): string (required only if the proxy is started with
  authentication pubkeys)
- the file: {transfer_id(string): signed_tx(string), ...}, with exactly the
  transfer IDs of `transfer_data`

Each transfer ID may belong to at most one operation on a given proxy: the
proxy keeps transfer IDs unique across all `ack.prepare` operations, mirroring
the transfer ID uniqueness already enforced by the recipient proxy on
`consignment.post`. This keeps a 1:1 mapping between a transfer ID and an
operation, so `ack.post` can identify the operation from the transfer ID alone
and an ACK signature cannot be replayed against a different operation.

The proxy resolves a call as follows:
- if none of the request's transfer IDs are registered, it registers a new
  operation and returns `result`: `true`
- if all of the request's transfer IDs are already registered, belong to the
  same single existing operation, and every field matches (the whole
  `transfer_data` and each per-transfer `signed_tx` from the file, plus
  `expires_at`, `signed_tx_hash` and `sender_pk`), it is an idempotent re-post
  and returns `result`: `false`
- if any transfer ID is already registered to a different operation (any other
  combination, including a partial overlap of transfer IDs across operations),
  the call is rejected with a "transfer ID in use" error
- if the request matches an existing operation by transfer IDs but a field
  differs, the call is rejected with a "cannot change" error

Response on success:
- `result`: `true` if the operation is newly registered
- `result`: `false` if the identical operation was already registered
  (idempotent)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- transfer ID in use
- cannot change (expiration | signed_tx | signed_tx_hash | recipient_pk |
  consignment_hash | sender_pk)
- invalid (expiration | transfer ID | recipient_pk | consignment_hash |
  signed_tx | signed_tx_hash | sender_pk | file | file_size): `signed_tx` is
  an entry of the file that isn't valid base64 or isn't for a transfer of
  `transfer_data`, `file` is a file that isn't a JSON object
- missing (expiration | transfer ID | recipient_pk | consignment_hash |
  signed_tx | signed_tx_hash | sender_pk | file_size): `signed_tx` is a
  transfer of `transfer_data` without an entry in the file
- missing file
- file too large: the declared `file_size` exceeds the maximum file size of
  this call (see the notes)
- signed TX too large
- invalid proxy auth signature
- too many items (transfer_data)

Notes:
- the expiration is mandatory to avoid inconsistency issues on the client side
- an identical re-post is idempotent only until the operation expires and while
  its signed TXs have not been removed (by `ack.clean`, after a NACK); after
  that it's refused (invalid `expires_at`, or cannot change `signed_tx`), since
  an expired operation can no longer be completed safely and a removal means
  the sender has already moved past `ack.prepare` in its flow
- anyone can call this endpoint but this requires knowledge of the transfer ID
  and also of TX encryption details; a 3rd party knowing the transfer ID can
  post a wrong TX, initiating a DoS attack, and this is hard to prevent (e.g.
  allowing the TX to be updated wouldn't solve the issue as the 3rd party could
  change it back) but doesn't need to be addressed, since the sender
  broadcasting the TX when retrieving the ACK acts as a fallback mechanism to
  ensure operation functionality
- this needs to be called by the sender before initiating the consignment.post
  call, so that a recipient is able to post an ACK (and retrieve the signed TX)
  right after getting and verifying the consignment
- donations are the exception: a donation carries the signed TX inside the
  consignment and is broadcast without an ACK, so for donations the sender
  skips `ack.prepare` (and the recipient skips `ack.post`); the sender-proxy /
  ACK / TX-release machinery only applies to non-donation operations
- the sender pubkey is necessary to allow authenticated calls to `ack.clean`
- `expires_at` can be invalid both because it's in the past and because it's
  too far in the future (exceeds the configured `max_expiry_secs`)
- the proxy should stop processing a request if the size of any signed TX
  exceeds the configured max signed TX size, advertised as
  `max_signed_tx_size` via `server.info` (e.g. 150 KiB, which should be more
  than enough for 1000 outputs), measured as the length of the base64 signed
  TX string, to avoid storage exhaustion DoS attacks
- the proxy should refuse to process a request with more than the configured
  max transfer IDs, advertised as `max_transfers` via `server.info` (e.g.
  1000), lest it would remain vulnerable to DoS attacks via huge number of
  transfers, each with a TX as big as possible
- the max file size (`max_file_size`) does not apply to this call: the file
  holds up to `max_transfers` signed TXs, so its maximum size is `max_transfers`
  times (`max_signed_tx_size` plus 70 bytes, which are the 64 characters of the
  transfer ID, its quotes, the colon and the separator of the JSON object
  entry), and the proxy must accept at least that (it can allow a little more,
  e.g. for whitespace or the enclosing braces); the declared `file_size` is
  checked against it (see 4.4.15), while the total uploaded data is checked as
  for the other uploads. It is not advertised in `server.info`, as clients can
  compute it from `max_transfers` and `max_signed_tx_size`
- the proxy processes a call in the following order:
  1. the request: it must be a single call (not a JSON-RPC batch) with a JSON
     body within the size limit (see 4.4 general notes)
  2. missing parameters, then invalid ones (see 4.4 general notes)
  3. `transfer_data` must have at most `max_transfers` transfers
  4. the upload checks (see 4.4.15), against the maximum file size of this call
  5. the proxy auth signature, if the proxy requires it
  6. the file content: it must be a JSON object with exactly the transfer IDs
     of `transfer_data`, each with a valid base64 signed TX not exceeding
     `max_signed_tx_size`
  7. the registration of the operation, as described above

#### 4.4.5 extended endpoint: `consignment.post`

When posting a consignment, the sender includes:
- the sender transport endpoint
- the sender pubkey
- the consignment hash
- the consignment size
- the invoice ID the transfer belongs to
- a signature proving ownership of the transfer ID
- a proof of work (see Appendix C)
- if the operation is part of a batch, via a dedicated bool parameter

The sender also optionally specifies:
- if the operation is a donation, by including the signed TX in the consignment

A successful call creates the transfer under the invoice, counting towards its
quota.

The signature is made with the secret key corresponding to `sender_pk` and the
message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of `transfer_id`, `consignment_hash`, `blob_hash` (see 4.2) and the
literal string `consignment`, with no separators. Since `blob_hash` is computed
by the proxy over the uploaded bytes, the signature also binds the exact
uploaded file. The literal string keeps this signature distinct from the
`media.post` one, whose message has the same shape, so a captured signature
cannot be replayed on the other call.

Changed parameters (replacing `recipient_id`):
- `transfer_id`: string

New parameters:
- `invoice_id`: string
- `sender_transport_endpoint`: string
- `sender_pk`: string
- `consignment_hash`: string
- `file_size`: string (bytes)
- `signature`: string
- `pow_timestamp`: string (unix absolute timestamp, seconds, UTC)
- `pow_nonce`: string (1 to 64 printable ASCII characters, 0x20-0x7e)
- `batch`: bool

Removed parameters:
- `txid`
- `vout`

Response on success:
- `result`: `true` if the transfer is newly created
- `result`: `false` if the identical transfer was already created (idempotent)

The proxy keeps the metadata of each transfer (including the uploaded file
hash) even after its data has been deleted via `transfer.retrieved`, so it can
still recognize an identical re-post.

The proxy processes a call in the following order:
1. missing parameters, then invalid ones (see 4.4 general notes), then the
   upload checks (see 4.4.15)
2. if the transfer ID already exists with identical data, the call is an
   idempotent re-post and returns `result`: `false`, ignoring the proof of work
3. the invoice ID must be reserved and not expired, the transfer ID must match
   the one derived from `invoice_id` and `sender_pk` (see 4 introduction), the
   signature must be valid and the transfer ID must not have been deleted via
   `transfer.delete`
4. if the transfer ID already exists with different data, the call is rejected
   with a "cannot change" error listing the differing fields
5. the invoice quota must not be full
6. only if the current proof of work difficulty for the invoice is greater than
   0, the proof of work must be valid (see Appendix C)

The "cannot change" error comes after the signature verification, so only the
actual sender (the holder of the `sender_pk` secret key) can learn that a
transfer with its transfer ID already exists with different data, and which
fields differ.

New errors:
- invoice not reserved: no reservation exists for the invoice ID
- expired: the invoice expiration has passed
- invoice quota exceeded: the invoice already has as many transfers as its
  quota allows
- transfer ID deleted: the transfer ID has been deleted via `transfer.delete`
  and cannot be reused
- invalid endpoint auth signature
- invalid proof of work: the proof of work does not satisfy the current
  difficulty or its `pow_timestamp` is outside the allowed window (see Appendix
  C.2); the current difficulty is returned in the error so the sender can
  retry
- cannot change (sender_transport_endpoint | sender_pk | consignment_hash |
  batch | file)
- invalid (transfer ID | invoice ID | sender_transport_endpoint | sender_pk |
  consignment_hash | batch | pow_timestamp | pow_nonce); for the proof of work
  fields, this only covers malformed values
- missing (transfer ID | invoice ID | sender_transport_endpoint | sender_pk |
  consignment_hash | batch | signature | pow_timestamp | pow_nonce)

Notes:
- the invoice ID must have been reserved via `invoice.prepare`; the consignment
  is stored under the transfer, which inherits the invoice expiration for
  retention
- the signature prevents third parties that learn the transfer ID (e.g. from
  the sender proxy or from another transport endpoint where the same transfer
  was posted) from taking it over with a different file, even by replaying a
  signature they have seen, since it would only be valid for the identical
  file
- the sender picks a fresh key pair for each operation, so no one else can
  create a transfer with its transfer ID; a sender reusing its key pair only
  collides with itself
- the proof of work fields (`pow_timestamp`, `pow_nonce`) are mandatory even
  when the current difficulty is 0, in which case any value is accepted (see
  Appendix C)
- a `transfer ID deleted`, `expired` or `invoice quota exceeded` error means
  that the transfer cannot be created on this transport endpoint; the sender
  can try the other transport endpoints listed in the invoice and must not
  broadcast the TX unless the transfer has been created on one of them (see
  6.4)
- the sender transport endpoint must be in the `RgbTransport` format (from the
  `rgb-invoicing` crate), which includes the protocol (e.g. `rpc://`), as this
  allows different kinds of RGB transports to be used, provided they offer the
  required functionality
- the `consignment_hash` is the hex-encoded SHA-256 of the plaintext
  consignment; it feeds the ACK message (and also the encryption nonce, see
  Appendix A); the proxy stores it as opaque metadata and must not validate it
  against the hash of the uploaded (possibly encrypted) file
- the `file_size` parameter allows the proxy to check if the file that's
  being uploaded is below the maximum allowed size
- `txid` and `vout` parameters dropped as those info are now derived from
  consignment terminals

The recipient also optionally receives:

New response fields:
- `sender_transport_endpoint`: string
- `sender_pk`: string
- `consignment_hash`: string
- `batch`: bool

Removed response fields:

- `vout`

#### 4.4.7 extended endpoint: `media.post`

Media is addressed per transfer: instead of a single `attachment_id`, the
sender references the transfer ID and the per-media identifier `media_id` (the
shared-secret-keyed value defined in Appendix A.9). A transfer may have
several media attachments, each distinguished by its `media_id`.

The call needs to be authenticated to prevent 3rd parties that learn a
`media_id` (e.g. from another transport endpoint where the same transfer was
posted) from taking it over with a different file. The signature is made with
the secret key corresponding to the `sender_pk` stored for the transfer by
`consignment.post` and the message to sign is the SHA-256 hash of the
concatenation, encoded as UTF-8 bytes, of `transfer_id`, `media_id`,
`blob_hash` (see 4.2) and the literal string `media`, with no separators. The
literal string keeps this signature distinct from the `consignment.post` one,
whose message has the same shape, so a captured signature cannot be replayed
on the other call.

Changed parameters (replacing `attachment_id`):
- `transfer_id`: string
- `media_id`: string
- the optionally encrypted media file

New parameters:
- `file_size`: string (bytes)
- `signature`: string

Response on success:
- `result`: `true` if newly stored
- `result`: `false` if the identical file was already stored for this
  `transfer_id` + `media_id` pair (idempotent)

New errors:
- transfer not found: no transfer exists for the transfer ID
- cannot change file: a different file was already posted for this
  `transfer_id` + `media_id` pair
- invalid endpoint auth signature
- too many media: the transfer already has the maximum number of media

Notes:
- the transfer must have been created via `consignment.post`, so media is
  posted after the consignment; the media is stored under the transfer and
  inherits the invoice expiration for retention
- the proxy stores media keyed by (`transfer_id`, `media_id`); posted files
  are immutable and `media_id` is opaque to the proxy, which must not try to
  relate it to the stored (possibly encrypted) bytes
- the proxy keeps the uploaded file hash of each media even after its data has
  been deleted via `transfer.retrieved`, so it can still recognize an identical
  re-post
- media can be posted for an existing transfer regardless of the invoice
  expiration, as long as the transfer data has not been retrieved: a transfer
  created right before the expiration must be able to receive its media, since
  the sender doesn't broadcast the TX until the media has been posted (see
  6.4); the media inherits the invoice retention like the consignment
- the `file_size` parameter allows the proxy to check if the file that's
  being uploaded is below the maximum allowed size
- the proxy should refuse a new media for a transfer that already has the
  configured max media, advertised as `max_media` via `server.info` (e.g. 10),
  lest it would remain vulnerable to storage exhaustion DoS attacks via a huge
  number of media posted to a single, cheaply created transfer; each proxy
  chooses its own value; an identical re-post stores nothing, so it's
  idempotent and doesn't count
- parameters are validated first, then the upload checks (see 4.4.15) are
  applied

#### 4.4.8 extended endpoint: `media.get`

When getting a media attachment, the recipient references the transfer ID and
the per-media identifier instead of a single `attachment_id`.

Changed parameters (replacing `attachment_id`):
- `transfer_id`: string
- `media_id`: string

The response returns the stored (possibly encrypted) media bytes.

New errors:
- transfer data retrieved: the transfer data has been deleted after a
  successful call to `transfer.retrieved`

Notes:
- the `media_id` is opaque to the proxy, the recipient derives it with the
  shared protocol with the sender; the reference (see Appendix A.9) uses the
  media digest and the shared secret (shared secret derivation uses the sender
  pubkey, which needs to be retrieved from the `consignment.get` response)

#### 4.4.9 new endpoint: `ack.clean`

Allow the sender to remove the signed TXs from an operation that was previously
created with `ack.prepare` and whose signed TX has not been released yet (not
all transfers have been ACKed).

The call needs to be authenticated to prevent 3rd parties from removing TXs for
arbitrary operations, so the sender(s) will need to sign the message using the
secret key corresponding to the `sender_pk` sent in the `ack.prepare` call. The
message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of all the lexicographically sorted transfer IDs, with no separators.

The call needs to uniquely identify an operation, for which transfer IDs are
sufficient (as they're guaranteed to be unique across a proxy instance).

If all transfers have already been ACKed, this call must return an error, as
the signed TX has been released and the recipients broadcast it as soon as they
obtain it (see 6.4). The call is allowed after partial responses, while after a
NACK there is no signed TX left to remove.

Parameters:
- `transfer_ids`: array of transfer_id(string)
- `signature`

Response on success:
- `result`: `true` if any signed TX was present and all are now removed
- `result`: `false` if there was none left (idempotent)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- operation not found
- invalid endpoint auth signature
- already acked
- too many items

Notes:
- the transfer IDs must match those registered via `ack.prepare`
- the proxy should refuse a request with more than the configured max
  transfer IDs (`max_transfers` via `server.info`, see 4.4.4) without looking
  them up, since an operation can't have more
- `ack.clean` removes the signed TXs (one per transfer) but keeps the operation
  record (and thus the reservation), so transfer IDs are not freed for reuse
  and the 1:1 mapping is preserved; a later `ack.post` still resolves the
  operation but no TX will be released
- the proxy must process `ack.clean` and `ack.post` calls for the same
  operation atomically with respect to each other, so that either the signed
  TXs are removed before the last ACK is registered, in which case no TX is
  released, or the last ACK is registered first, in which case `ack.clean` is
  refused; a sender can thus rely on a successful `ack.clean` to fail the
  operation, knowing the signed TX has not been and will not be released
- the signed message is static (for the example `transfer_ids` = `["tidB",
  "tidA"]` the message is `tidAtidB`), so an attacker that were to capture the
  signature could replay it; the severity is low though, since the signature is
  meant to be sent over TLS and the replay can only work for an identical
  transfer ID set, which contains high-entropy transfer IDs and for which the
  TXs will have already been removed

#### 4.4.10 extended endpoint: `ack.post`

When posting a N/ACK, the recipient includes its signature.

When a recipient posts an ACK, if the transfer ID has been registered to an
operation with `ack.prepare` and the operation has not yet expired, the proxy
registers the response and releases the signed TX (except for batch transfers,
see notes). When a recipient posts a NACK, the proxy registers the response but
doesn't release the signed TX.

When a call is received for an unregistered transfer ID or for an expired
operation an error is returned.

Successive calls with the same data are idempotent, returning the same data,
including past the expiration and until the retention policy kicks in.

Changed parameters (replacing `recipient_id`):
- `transfer_id`: string

New parameter:
- `signature`: string

New response fields on a valid ACK before the expiration:
- `sender_pk`: string
- `signed_tx_hash`: string (hex-encoded SHA-256 of the plaintext TX, shared by
  all recipients)
- `signed_tx` (optional): string (the signed TX for the recipient)

New response field on every successful response (ACK or NACK, re-posts
included):
- `expires_at`: string (the operation expiration, unix absolute timestamp,
  seconds, UTC)

New errors:
- cannot change signature
- expired
- invalid content signature
- operation not found

Removed errors:
- consignment not found: no longer can be returned, as the sender proxy isn't
  guaranteed to be the same as the recipient proxy anymore

Notes:
- since each transfer ID maps to exactly one operation (`ack.prepare` keeps
  transfer IDs unique), the single `transfer_id` provided here unambiguously
  identifies the operation; an unregistered transfer ID yields the "operation
  not found" error
- when more than one transfer was provided via `ack.prepare` (i.e.
  transfer_data length > 1), the proxy must not release the TX until all
  transfers have been ACKed; the last recipient to ACK receives the TX right
  away, all others can get it by calling `ack.post` again (idempotent). If at
  least 1 transfer has not been ACKed or has been NACKed, the TX must not be
  released
- knowledge of which recipients N/ACKed an operation relies on the fact that
  there can only be a single sender proxy (as specified in `consignment.post`),
  lest recipient ACK responses could be scattered across multiple instances,
  with no way to get the full picture by any of those
- after the expiration has passed, the proxy must not release the signed
  TX, even if a valid ACK is received, and instead return an error, since the
  sender might have failed the operation at this point
- after the expiration has passed, the proxy keeps the operation, its ACK
  values and signatures and, if every transfer has been ACKed, the released
  signed TXs until the retention grace after the expiration has passed (see
  4.6), so that the sender can retrieve the proofs of acknowledgement and
  recipients can still retrieve a released TX by posting their ACK again
- if the call succeeds but the TX is not released (which happens e.g. for batch
  operations), the recipient must not consider the operation to have progressed
  (e.g. to a "waiting confirmation" state) as the TX might never get broadcast
  (e.g. in case another batch participant NACKs); the operation needs to be
  considered "waiting for broadcast" (e.g. a dedicated status or an `acked`
  flag on the operation)
- after receiving a NACK, the signed TX can be safely deleted
- a recipient broadcasts the signed TX as soon as it obtains it, and saves it
  so it can broadcast it again (e.g. if it exits the mempool due to low fees),
  but only until the broadcast deadline (see 6.4)
- the operation `expires_at` is returned so that every party of the operation
  shares the same rebroadcast and failure deadline (see 6.4), since recipients
  otherwise only know their own invoice expiration
- the `sender_pk` is returned here to allow recipients to use it directly to
  decrypt (see Appendix A); this also allows the `sender_pk` registered via
  `ack.prepare` to differ from the one used on `consignment.post` (from which
  the transfer ID and the witness seal blinding factor are always derived),
  though this is not required

#### 4.4.11 extended endpoint: `ack.get`

When getting an ACK, the sender also retrieves the ACK signatures (one per
recipient).

The call needs to be authenticated to prevent 3rd parties from causing the ACK
data to be deleted before the sender has had a chance to retrieve it.
The signature needs to be done using the sender key associated to the operation
that corresponds to the provided transfer IDs. The message to sign is the
SHA-256 hash of the concatenation, encoded as UTF-8 bytes, of all the
lexicographically sorted transfer IDs followed by the timestamp, with no
separators.

The timestamp must be within 300 seconds of the proxy clock to be considered
valid. No replay attacks inside this window are problematic since the sole
purpose of the authentication is to guarantee that the sender has a chance to
retrieve the data before anyone else. Replay attacks outside this window could
be problematic since a transfer ID might be reused after a proxy has been
reset.

Modified parameter (replaces the existing `recipient_id`):
- `transfer_ids`: array of transfer_id(string)

New parameters:
- `signature`: string
- `timestamp`: string (unix absolute timestamp, seconds, UTC)

New response fields:
- `acks`: {transfer_id(string): ack(bool), ...}
- `signatures`: {transfer_id(string): signature(string), ...}

Removed errors:
- consignment not found: no longer can be returned, as the sender proxy isn't
  guaranteed to be the same as the recipient proxy anymore

New errors:
- operation not found
- invalid endpoint auth signature
- invalid timestamp
- too many items

Notes:
- all the transfer IDs must belong to the same operation, lest the signature
  would be invalid for at least one of them
- the proxy should refuse a request with more than the configured max
  transfer IDs (`max_transfers` via `server.info`, see 4.4.4) without looking
  them up, since an operation can't have more
- the sender should save the ACK values and signatures as part of the operation
  metadata, as proof of acceptance by the recipients; the sender should also
  have saved the invoices (from which the transfer IDs are derived) that
  originated the operation, to demonstrate who they came from (e.g. via mail)
  and tie ACKs to specific counterparties
- calling this API does not trigger the deletion of the operation data, which
  is kept until the retention grace after the expiration has passed (see 4.6),
  as recipients may still need to retrieve a released signed TX via `ack.post`
- an "operation not found" error for an operation the sender successfully
  registered with `ack.prepare` means the proxy lost its data (e.g. it was
  reset); see section 6.2 for how the sender should proceed

#### 4.4.12 new endpoint: `transfer.list`

Allow the recipient to list the transfers created for an invoice, which it
cannot know in advance since transfer IDs are derived from the sender keys.

The call needs to be authenticated to prevent 3rd parties from learning the
transfers of an invoice (e.g. a public one), so the recipient will need to sign
the message using the secret key corresponding to the invoice pubkey
registered via `invoice.prepare`. The message to sign is the SHA-256 hash of
the concatenation, encoded as UTF-8 bytes, of `invoice_id` followed by the
timestamp, with no separators.

The timestamp must be within 300 seconds of the proxy clock to be considered
valid, so that a captured signature cannot be replayed to keep listing the
transfers of the invoice.

Parameters:
- `invoice_id`: string
- `signature`: string
- `timestamp`: string (unix absolute timestamp, seconds, UTC)

Response on success:
- `result`: a map from transfer ID to its state:
    - `pending`: the transfer data (consignment and media) is available
    - `retrieved`: the transfer data has been deleted via `transfer.retrieved`,
      while the transfer still counts towards the invoice quota

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- invoice not reserved: no reservation exists for the invoice ID
- invalid endpoint auth signature
- invalid timestamp

Notes:
- the "invoice not reserved" error is returned before verifying the
  signature, since the pubkey to verify it with is only known for reserved
  invoices; this discloses nothing that `invoice.check` does not already
  disclose, and lets the recipient distinguish a reservation lost in a proxy
  data wipe from one taken by someone else (see 6.4); after the invoice
  expiration it can also mean that the data was deleted because no transfer
  was pending (see 6.1)
- transfers deleted via `transfer.delete` are not listed
- the recipient then retrieves each pending transfer via `consignment.get` and
  `media.get` and, once it has saved its data, calls `transfer.retrieved` (or
  `transfer.delete`)

#### 4.4.13 new endpoint: `transfer.retrieved`

Allow the recipient to signal that it has retrieved and saved the data of a
transfer, so the proxy can delete its consignment and media, while the
transfer keeps counting towards the invoice quota (e.g. so that a single-use
invoice stays full).

The call needs to be authenticated to prevent 3rd parties from deleting the
transfer data, so the recipient will need to sign the message using the secret
key corresponding to the invoice pubkey registered via `invoice.prepare`. The
message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of `transfer_id` and the literal string `retrieved`, with no separators.

Parameters:
- `transfer_id`: string
- `signature`: string

Response on success:
- `result`: `true` if the transfer has been marked as retrieved
- `result`: `false` if the transfer had already been marked as retrieved or
  deleted (idempotent)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- transfer not found: no transfer exists (nor has been deleted) for the
  transfer ID
- invalid endpoint auth signature

Notes:
- the "transfer not found" error is returned before verifying the signature,
  for the same reason as in `transfer.delete`
- the proxy deletes the consignment and media of the transfer but keeps its
  metadata (file hashes and sender data), so that idempotent re-posts via
  `consignment.post` and `media.post` keep working; `consignment.get` and
  `media.get` instead return a "transfer data retrieved" error
- the recipient must only call this once the transfer data has been durably
  saved, since it cannot be retrieved from the proxy again
- a retrieved transfer can still be deleted via `transfer.delete`, e.g. to
  free its quota slot after refusing it
- the literal string in the signed message keeps this signature distinct from
  the `transfer.delete` one, so a captured signature cannot be replayed to
  perform the other action
- a group of recipients sharing an invoice (e.g. multisig cosigners) cannot
  expect each member to retrieve the data from the proxy: the first member
  retrieving it shares it with the others by other means

#### 4.4.14 new endpoint: `transfer.delete`

Allow the recipient to delete a transfer it no longer needs (e.g. a settled,
refused or fake one), removing its consignment and media and freeing one slot
of the invoice quota.

The call needs to be authenticated to prevent 3rd parties from deleting
transfers, so the recipient will need to sign the message using the secret key
corresponding to the invoice pubkey registered via `invoice.prepare`. The
message to sign is the SHA-256 hash of the concatenation, encoded as UTF-8
bytes, of `transfer_id` and the literal string `delete`, with no separators.

Parameters:
- `transfer_id`: string
- `signature`: string

Response on success:
- `result`: `true` if the transfer has been deleted
- `result`: `false` if the transfer had already been deleted (idempotent)

Response on failure:
- `error`: `{ "code": <code>, "message": "<string>", "data": <object> }`, with
  `data` optional (see 4.4 general notes)

Errors:
- transfer not found: no transfer exists (nor has been deleted) for the
  transfer ID
- invalid endpoint auth signature

Notes:
- the "transfer not found" error is returned before verifying the signature,
  since the pubkey to verify it with is only known for the invoice of an
  existing transfer; this discloses nothing that `consignment.get` does not
  already disclose
- a transfer can be deleted both while pending and after being marked as
  retrieved via `transfer.retrieved`
- the proxy keeps a record of deleted transfer IDs until the invoice data is
  deleted (see 4.6), so a transfer ID cannot be reused (`consignment.post` returns a
  "transfer ID deleted" error) and the 1:1 mapping between a transfer ID and a
  transfer is preserved
- the signed message is static, but a replayed signature can only delete the
  same transfer again, which has no effect since it cannot be recreated; the
  literal string keeps it distinct from the `transfer.retrieved` signature
- the invoice reservation is never deleted by this call: it is only freed once
  its expiration has passed, lest anyone knowing the (possibly public) invoice
  could reserve it again with their own pubkey and quota
- there is no way to close an invoice before its expiration, since the invoice
  may have been shared publicly and senders rely on its expiration
- the recipient should only delete transfers that are in a final status (e.g.
  settled or refused) and whose data it has saved, since deleted data cannot be
  retrieved again

#### 4.4.15 DoS prevention

Endpoints that accept file uploads take a `file_size` parameter, in bytes, that
expresses the size of the file that's being uploaded.

The proxy should have a configured maximum size limit, advertised as
`max_file_size` via `server.info`, and refuse uploads that exceed it, in order
to avoid storage exhaustion DoS attacks. This applies to `consignment.post` and
`media.post`; the file of `ack.prepare` holds the signed TXs of a whole
operation and has its own maximum, derived from `max_transfers` and
`max_signed_tx_size` (see 4.4.4), which is checked in the same way.

The proxy cannot trust the received `file_size` to be correct though, so it
should also check the total uploaded data size as it's received and abort the
upload if the size received in `file_size` parameter is exceeded.

To make this possible, the multipart `params` part must precede the file part,
so that the declared size is known while the file is received. The upload
checks, applied while receiving the request and right after the parameter
validation, are:
- a file part arriving before `params` is refused as invalid (`file`)
- a declared `file_size` above the maximum of the call is refused as "file too
  large"
- a missing file is refused as "missing file"
- the received file must be exactly `file_size` bytes, otherwise it's refused
  as invalid (`file_size`), with a larger file aborted as soon as it exceeds
  the declared size

A received file cannot exceed the maximum without first exceeding its declared
size, so "file too large" only means that the declared size exceeds the proxy
maximum, while any mismatch between the declared and the actual size is a
malformed request.

The multipart request also needs bounds on the number and size of its form
fields, so the proxy should limit them (e.g. to the fields of a call listing
`max_transfers` transfers), and a request with a single file part. The `params`
can be sent either as a single JSON-encoded field, which every proxy must
support and is the only option for calls with nested parameters
(`ack.prepare`), or optionally as one `params[<name>]` field per parameter; in
both cases the parameters must precede the file.

JSON-RPC batches and oversized JSON bodies are refused as well (see 4.4 general
notes), so the cost of a request is bounded by the limits of its single call.

Invoices can be shared publicly, so anyone can create transfers for them via
`consignment.post`, possibly filling their quota with fake transfers. Recipients
can delete unwanted transfers via `transfer.delete` and the proxy can require
an adaptive proof of work on `consignment.post`, whose difficulty is 0 during
normal operation and rises while an invoice or the whole proxy is under
attack. The mechanism is specified in Appendix C.

### 4.6 data retention

Every artifact the proxy stores is per-invoice or per-transfer and tied to an
expiration:
- the recipient proxy stores the invoice reservation, its transfers (including
  the records of deleted ones), their consignment and their media under the
  expiration provided to `invoice.prepare`
- the sender proxy stores the ACK data under the expiration provided to
  `ack.prepare`

Once an expiration has passed, most of the corresponding data is useless: no
new transfers can be created for an expired invoice, a settled or failed
operation no longer needs its consignment/media, and the proxy must never
release a signed TX after expiration. A proxy can, and should, implement a
data retention policy that deletes the expired data to reclaim storage, with
the exceptions detailed below.
Deleting an expired reservation frees its invoice ID and the transfer IDs of its
transfers; this is acceptable because invoice ID and transfer ID uniqueness
already cannot be relied upon across proxy data wipes (see the signatures note
in section 5) or across different transport endpoints, a new invoice always
uses a fresh pubkey (hence a fresh invoice ID) anyway and a new operation always
uses a fresh sender key (hence a fresh transfer ID). A reservation must not be
deleted before its expiration, even if all of its transfers have been deleted
via `transfer.delete` (see 4.4.14).

A recipient proxy must not delete the data of pending transfers (neither
retrieved via `transfer.retrieved` nor deleted via `transfer.delete`) right
after the invoice expiration, as the recipient might not have already
downloaded it, thus losing access to the received assets. Examples are a
transfer created right before the expiration, a recipient that has been
offline, and a donation (whose TX has already been broadcast). Pending
transfers are kept until a configurable retention grace after the invoice
expiration has passed, advertised as `retention_grace_secs` via `server.info`,
along with the invoice reservation and its transfer records, which are needed
to authenticate the recipient calls. Once no pending transfer is left or the
retention grace has passed, all the invoice data can be deleted. The signal
that a transfer has been retrieved needs to be authenticated, which is why it
is given via `transfer.retrieved` (or `transfer.delete`) rather than inferred
from `consignment.get` and `media.get` calls, which anyone knowing the transfer
ID could make.

Once the expiration of an operation has passed, a sender proxy can delete its
signed TXs if not all of its transfers have been ACKed or at least one has been
NACKed, since they can no longer be released. Everything else is kept until the
retention grace after the expiration (`retention_grace_secs`) has passed:
the operation record, needed to authenticate the calls, the ACK values and
signatures, which the sender might not have downloaded yet and would otherwise
lose as proofs of acknowledgement, and, if all the transfers have been ACKed,
the released signed TXs, which recipients that haven't obtained them yet (e.g.
batch participants or recipients that have been offline) can still retrieve by
posting their ACK again. The data is kept for the whole retention grace
regardless of `ack.get` calls, so that recipients can rely on it, while the
grace still caps how long it is kept, lest it could be kept forever (e.g. by an
attacker that never calls `ack.get`, or by a sender that never comes back),
defeating the bounded retention guaranteed by the maximum expiration.

The expiration cannot be arbitrarily far in the future: a proxy enforces a
maximum expiration (a configurable cap with a sensible default, e.g. 1 month).
`invoice.prepare` and `ack.prepare` reject an `expires_at` beyond the cap
rather than silently clamping it, so the client always knows the exact
expiration in effect. Silently clamping it would de-sync the sender's view of
the TX-release window (see section 6) and the recipient's view of how long its
data stays available. The cap guarantees stored data is cleaned up within a
bounded time frame and prevents a caller from pinning data on the proxy
indefinitely (a storage-exhaustion DoS) via a very long expiration.

A proxy advertises its cap as `max_expiry_secs` via `server.info`, so clients
can choose a valid `expires_at` up front, leaving some margin for client/proxy
clock skew.

Operators who need longer-lived data should run their own proxy with a higher
(or no) cap; such a proxy should enable the optional authentication on
`invoice.prepare` / `ack.prepare` to avoid reopening the storage-exhaustion DoS
to anyone via the higher cap.

Once some data can be deleted, it is recommended to keep it available for some
additional time, to allow clients that could have experienced some issue to
retry and leverage the idempotent nature of APIs to recover.

Note: the current reference proxy stores data with no timestamp or expiration,
so the retention machinery is entirely new.

## 5 security notes

- keys: key generation requires a source of good quality randomness, which
  might not be available in some environments (e.g. embedded)
- identity: both senders and recipients use fresh key pairs (per operation and
  per invoice respectively, see A.10), so counterparts and proxies cannot link
  a party's identity across operations or invoices through its keys; all the
  transfers to the same invoice share its pubkey (see the linkability note)
- signatures: the proxy prevents transfer ID reuse (the recipient proxy for
  `consignment.post`, including deleted transfers, and the sender proxy for
  `ack.prepare` operations), which keeps a 1:1 transfer-ID-to-operation mapping
  and prevents replay of ACK signatures across operations, though this cannot
  be relied upon outside of the operation scope (and in general) as the proxy
  data can be wiped and this cannot be detected from the client side
- trust: senders trust their proxy of choice to correctly verify signatures and
  keep signed TXs private while no valid ACKs have been received, not all
  recipients in a batch operation have ACKed or if an operation has expired
- compatibility: clients can refuse to carry out an operation using an
  operation mode (e.g. cleartext consignment and media) if it doesn't provide
  some guarantees they require
- privacy: the transport endpoint might reveal part of the counterpart's
  infrastructure to the counterpart
- media: encrypted media attachments are protected; they are also addressed by
  an opaque `media_id` rather than the plaintext digest (see Appendix A.9), so
  an observer holding a candidate cleartext cannot recognize which (encrypted)
  media is transferred and the proxy cannot correlate the same media across
  recipients or transfers
- consignment: the `consignment_hash` is sent in the clear; this is a lower
  risk (a consignment is transfer-specific, not a known-plaintext corpus) and
  it is required in the clear by the sender proxy to reconstruct and verify the
  ACK message, so it is intentionally not hidden the way `media_id` is
- MITM: if the channel over which the invoice is sent or `consignment.post`
  happens is not authenticated, an attacker between the two counterparts could
  replace the exchanged data with its own and intercept, decrypt, tamper with
  and re-encrypt it undetected. Invoice authentication is already a requirement
  (otherwise an attacker could change the beneficiary and get the funds), so
  this proposal introduces no new requirement; proxy API calls should happen
  over an authenticated channel (TLS) regardless
- DoS: anyone knowing an invoice can create transfers for it, possibly filling
  its quota with fake ones; the optional proxy authentication protects the
  proxy storage (only authorized recipients can reserve invoices) but not the
  availability of invoices, since `consignment.post` must remain open to any
  sender; the adaptive proof of work (Appendix C) makes spam at scale expensive
  and recipients can restore the quota via `transfer.delete`, but a determined
  attacker can still keep a single invoice full for a while, especially while
  the recipient is offline and cannot delete fake transfers; honest senders
  learn this before broadcasting, so no funds are at risk
- linkability: all transfers to an invoice share its pubkey and beneficiary, so
  they can be linked to each other, on-chain when an address is reused and
  off-chain (identical concealed seal) when a blinded UTXO is reused; the
  recipient accepts this when reserving an invoice with a quota greater than 1
- invoice ID: the recipient proxy stores the invoice pubkey, so it could link
  invoice IDs to known beneficiaries (e.g. addresses that appear on-chain) by
  computing their invoice IDs; this is accepted, since a recipient that wants
  to avoid it can run its own proxy
- rebroadcast: recipients stop rebroadcasting a signed TX at the broadcast
  deadline (see 6.4), but this narrows rather than closes the window in which
  the TX could still confirm, since any node that saw it can rebroadcast it and
  only spending one of its inputs (which only the sender can do) invalidates
  it; this is why recipients broadcast the TX as soon as they obtain it, why
  recipients add a confirmation margin after the deadline before failing, and
  why recipients of blind invoices keep a residual risk of losing assets if they
  spend the blinded UTXO after failing such a transfer
- blinded UTXO spent too early: transfers created before the invoice
  expiration can still be downloaded until the end of the retention grace, and
  a donation's TX is broadcast before the recipient downloads it; a recipient
  spending the blinded UTXO before all the transfers are processed (see 6.1)
  loses the assets of the donations among them, as does a recipient that never
  manages to download a donation (e.g. because of a proxy data loss); this risk
  already exists for single-use blind invoices
- unreserved endpoint: a transport endpoint listed in the invoice but not
  reserved by the recipient (because the invoice was shared before reserving
  it, or because the reservation was lost in a proxy data wipe) can be
  reserved by anyone knowing the invoice; senders cannot tell, and transfers
  posted there are not visible to the recipient: non-donation operations just
  expire, while for donations, already broadcast, the sender needs to hand
  the consignment over by other means; this is mitigated by reserving the
  invoice on all endpoints before sharing it and by monitoring the
  reservations (see 6.4)

## 6 client behavior expectations

This section captures behavior a client implementation is expected to follow to
interoperate correctly. It is not enforced by the proxy but affects correctness
and safety across implementations.

### 6.1 expiration

All expirations are assumed to be in UTC.

A sender must never fail an operation before its expiration, lest its proxy
might release the signed TX of a now-locally-failed operation, leading to
inconsistencies.

A sender should set the `ack.prepare` expiration sufficiently before the
earliest invoice expiration among the operation recipients, leaving some margin
to detect the ACKs and broadcast the TX, so that the TX can only be released
while the recipients are still waiting for it (see 6.3).

The `ack.clean` endpoint lets the sender remove the stored signed TX, stopping
the proxy from accepting an ACK and releasing the signed TX, which allows the
sender to fail an operation before its expiration.
This also lets the sender avoid any issues due to clock discrepancies between
client and proxy by making sure the TX cannot be released before the operation
is failed.

Once the expiration has passed the proxy no longer accepts new ACKs, so the set
of responses is final. Before failing an expired operation the sender must call
ack.get, within the retention grace after the expiration (see 4.6):
- if at least one recipient has not ACKed (no response, or a NACK), the TX was
  never released and the operation can be failed
- if every recipient has ACKed, the TX has been released and the operation
  cannot simply be failed: if the invoice expiration of every recipient has not
  passed yet, the sender must progress the operation, broadcasting the TX
  itself (which is harmless if a recipient already did); otherwise it must not
  broadcast the TX, since a recipient that didn't obtain it (see 6.3) might
  have already failed the transfer, and instead progresses the operation if the
  TX is found on-chain or fails it after spending one of the TX inputs

Unlike the cases in which the sender cannot know whether the signed TX has been
released (a lost operation or an invalid ACK signature, see 6.2 and 6.3), where
failing the operation after the expiration while accepting the residual risk is
allowed, here the TX has certainly been released: compliant recipients hold it,
are expected to save and rebroadcast it, and consider the transfer progressed,
so its later confirmation is a likely outcome rather than a residual risk. The
sender can therefore only fail the operation after spending one of the TX
inputs, making it invalid. A sender that cannot do so keeps the operation
pending until the TX confirms (progressing it) or becomes invalid because one
of its inputs has been spent by another confirmed transaction (failing it).

A sender that fails an expired operation without checking the ACKs might fail
an operation whose TX later confirms.

A recipient may fail a non-donation operation before its expiration if an ACK
has not yet been posted to the sender proxy for it, typically by first posting
a NACK instead. For donations, the TX was included in the consignment so the
recipient can broadcast it (if not already done by the sender) and the
operation can be progressed to a "waiting confirmations" state.

The invoice expiration is also the time after which the recipient proxy no
longer accepts new transfers for the invoice. For a blind invoice, all
transfers assign assets to the same blinded UTXO, so the recipient must keep it
unspent until the invoice expiration has passed (plus some margin for clock
skew) and, for each transport endpoint listed in the invoice, either a
`transfer.list` call made after that point shows that all its transfers have
been retrieved and processed, or the retention grace of that proxy
(`retention_grace_secs`) after the expiration has passed; in both cases all
the accepted transfers must also have been settled or failed. Otherwise the
assets of a transfer created before the expiration but not yet downloaded
(e.g. a donation, whose TX has already been broadcast) would be assigned to an
already spent UTXO and be lost. Since a donation carries its signed TX, the
recipient broadcasts it itself after downloading the transfer (if not already
done by the sender) and keeps the blinded UTXO unspent until the donation is
settled (its TX confirmed) or failed, which for a donation only happens once
its TX can no longer confirm (e.g. one of its inputs has been spent by another
confirmed transaction). A non-donation transfer downloaded after the blinded
UTXO has been spent must be refused (by posting a NACK). A donation in the same
situation cannot be refused, since its TX has already been broadcast: its
assets are lost if the TX confirms, which the recipient can detect on-chain to
record the transfer as lost rather than failed.
After the invoice expiration, a proxy may already have deleted all the invoice
data, reservation included, because no transfer was pending (see 4.6), in
which case `transfer.list` returns "invoice not reserved". This cannot be told
apart from a data wipe that destroyed pending data: in both cases nothing more
can be retrieved, unless the proxy is restored from a backup. The recipient
chooses whether to treat it as no transfer pending on that proxy or to wait for
that proxy's retention grace, also covering a restore; the latter is safer for
invoices where losing a transfer matters more than keeping the UTXO locked.
Transfers accepted before the invoice expiration can be broadcast after it,
since the sender chooses the `ack.prepare` expiration independently. Witness
invoices have no such constraint, since each transfer creates a new UTXO.

### 6.2 data retention

The proxy keeps the recipient data (consignment, media) of pending transfers
until the retention grace after the invoice expiration has passed (see 4.6), but
can delete it after that even if the recipient has not downloaded it yet. In
this case the recipient is expected to fail the transfer or, for donations,
whose TX has already been broadcast, to obtain the consignment from the sender
by other means.

The proxy keeps the sender data (ACK + signature) until the retention grace
after the expiration has passed (see 4.6), so senders can expect to
successfully call `ack.get` within that time frame for the operations
successfully reserved with `ack.prepare`. This is important also
because senders are expected to call `ack.get` before failing an expired
transfer. Past the retention grace, `ack.get` may return "operation not found",
in which case the sender proceeds as described below and has no proof of
acknowledgement.

Since a proxy can be reset without the clients knowing, clients should always
check for the presence of the TX on-chain before failing a transfer. As a
notable example, a sender can find that its proxy no longer knows an operation
(`ack.get` returns "operation not found") and thus cannot learn whether the
recipients ACKed. Clients should always check for the presence of the TX
on-chain (mempool included) before failing a transfer. If the TX is found, the
transfer must be progressed instead of failed, as inconsistencies may otherwise
arise.
Not finding the TX gives no guarantee. An an example, a recipient might have
obtained the TX before the reset and broadcast it later, and a sender that
fails an operation in this situation accepts that risk (to rule it out it can
spend one of the inputs of the TX, making it invalid).

A sender finding that its proxy no longer knows an operation should not fail
it right away, but wait until the expiration plus the retention grace of the
sender proxy (`retention_grace_secs`) has passed (plus some margin for
clock skew), consistently with 6.1: the proxy might not have permanently lost
the operation data (e.g. it could be restored from a backup) and could still
release the signed TX before the expiration or return it to recipients that
already ACKed until the end of the retention grace, while recipients that
obtained the TX (or still can) have time to broadcast it, which the sender can
then detect on-chain. After that, the sender checks for the TX on-chain as
described above and fails the operation if it's not found, accepting the
residual risk, unless it prefers to spend one of the TX inputs.

### 6.3 caveats

Any party interacting with the proxy cannot assume anything about the
counterpart and can only operate based on the responses received from the
proxy. It can't be assumed that the counterparties have a communication
channel, so each situation needs to be dealt with by using the information each
party independently holds.

A notable example is a recipient calling `ack.post`, which succeeds, but the
response doesn't include the signed TX (even though the operation is not a
batch one).
This would be a case in which the proxy acts in a non compliant way. The sender
understands that the recipient is ok with the operation, but the recipient
needs to wait for the sender to broadcast the TX since it's not been returned.
The recipient can only handle the resulting situation in the best possible way.
In this case, the recipient:
- must not consider the transfer as progressed (i.e. waiting for confirmations)
- must not consider the transfer as failed (the sender can broadcast the TX)
- should consider the transfer as waiting for TX broadcast
- follows the rule for a successful ACK without TX in 6.4, eventually failing
  the transfer if the TX is not present on-chain
In this case, the sender:
- should broadcast the TX while the invoice expiration has not passed
- must not broadcast the TX after the invoice expiration has passed
- since it cannot tell this case apart from a compliant one, follows 6.1: it
  can only fail the operation after spending one of the TX inputs, otherwise
  keeping it pending (see 6.1)
In this case, both parties:
- as long as the transfer has not been failed, if the TX is found on-chain the
  transfer must be progressed (waiting for confirmations); failing the transfer
  is final

The invoice expiration is used here since it's the only one known to both
parties (the sender chooses the `ack.prepare` expiration independently).

Another notable example is a sender getting, via `ack.get`, an ACK whose
signature it cannot verify against the recipient pubkey, even though the proxy
is supposed to verify it before accepting it. The sender cannot tell whether
the proxy accepted an invalid ACK or a valid one was corrupted or tampered with
afterwards, so it must neither trust the ACK as proof of acceptance nor
broadcast the TX, and must also consider that the signed TX may have already
been released to the recipient. In this case the sender cannot use
`ack.clean`, which would be refused (or would not help) since the ACK has
already been registered, and instead:
- skips the `ack.clean` call (or ignores its error)
- waits until the expiration plus the retention grace of the sender proxy has
  passed (plus some margin for clock skew) and then checks for the TX on-chain,
  progressing the operation if the TX was found or, if not, either accepts the
  residual risk described in 6.2 or invalidates the TX by spending one of its
  inputs, and finally fails the transfer
- should not trust that proxy anymore, as it behaved in a non-compliant way

### 6.4 invoices and transfers

A sender:
- uses a fresh key pair for each operation, from which the transfer IDs of the
  operation are derived (see 4 introduction), and includes at most one transfer
  per invoice in an operation
- calls `invoice.check` before building the operation, to know whether the
  invoice can accept a transfer and which proof of work difficulty is required
- derives the witness seal blinding factor as specified in Appendix A.11,
  instead of choosing it
- does not broadcast the TX, including for donations, until calls to
  `consignment.post` and `media.post` have succeeded
- if `consignment.post` fails because the transfer cannot be created on a
  transport endpoint (e.g. invoice quota exceeded, expired invoice or transfer
  ID deleted), tries the other transport endpoints listed in the invoice, since
  each proxy enforces these independently; only if no listed transport endpoint
  accepts the transfer, it fails the operation, for non-donation operations
  after calling `ack.clean`; for a donation whose consignment (which includes
  the signed TX) has already been posted for another transfer of the
  operation, the TX can be broadcast by that recipient, so the sender can only
  fail the operation after spending one of the TX inputs, otherwise it
  completes the operation and hands the missing consignment over by other
  means
- if `consignment.post` fails with an "invalid proof of work" error (e.g.
  because the difficulty has risen), computes a new proof of work and retries,
  with no need to rebuild the operation
- does not create a transfer after the invoice expiration, even if a proxy
  still accepts it, and uses the pubkey and expiration from the invoice, never
  the data registered on the recipient proxy

A recipient:
- reserves the invoice on all the transport endpoints listed in the invoice
  before sharing it (see Appendix B)
- discovers the transfers of an invoice via `transfer.list` and must retrieve
  them before the end of the retention grace following the invoice expiration
  (see 4.6), since the proxy can then delete them
- verifies that the transfer ID matches the one derived from the invoice ID and
  the `sender_pk` returned by `consignment.get`
- keeps, for each invoice, the set of sender pubkeys of the transfers it
  accepted: a transfer with an already seen sender pubkey is accepted only if
  it has the same consignment hash (i.e. it's a retry of the same transfer,
  e.g. on a different transport endpoint), otherwise it's refused
- refuses a transfer whose terminal allocation paying the invoice (operation ID
  and assignment index) has already been credited for a different transfer ID,
  lest the same allocation would be credited twice
- for witness invoices, identifies the output paying the invoice by its script,
  its vout and the blinding factor derived as specified in Appendix A.11,
  refusing the transfer if no such output exists
- for blind invoices, identifies the allocation paying the invoice by the
  invoice concealed seal and keeps the blinded UTXO unspent as detailed in 6.1
- before posting an ACK, reads `retention_grace_secs` from the `server.info`
  of the sender proxy and posts a NACK instead if it's below its acceptable
  minimum (e.g. shorter than how long it could be offline): the grace is chosen
  by the sender's proxy and can be small or even 0, in which case a recipient
  that doesn't obtain the TX right away can only rely on it being broadcast
  before the operation expiration
- considers as broadcast deadline (`D`) the operation `expires_at` returned by
  `ack.post` plus the `retention_grace_secs` of the sender proxy, and as
  confirmation margin an additional waiting time after `D`, chosen by the
  client (e.g. one day), that gives a TX broadcast shortly before `D` time to
  be confirmed and also covers clock differences
- broadcasts the signed TX as soon as it obtains it from `ack.post`, so it
  reaches the chain even if the sender doesn't broadcast it, and saves it to
  broadcast it again if needed, but only until `D`; then, if the TX gets
  confirmed by `D` plus the confirmation margin, it progresses the transfer,
  otherwise it fails it, accepting the risk that the TX, rebroadcast by
  someone else, is confirmed later
- after a successful ACK without TX (e.g. a batch operation not yet ACKed by
  every recipient, or a non-compliant proxy), keeps the transfer waiting for
  broadcast and posts the same ACK again until:
    - the TX is returned, in which case it broadcasts it and progresses the
      transfer
    - "operation expired" is returned, meaning that the TX has never been
      released and never will be, in which case it fails the transfer
    - "operation not found" is returned, or no definite answer is obtained by
      `D`, in which case it waits until `D` plus the confirmation margin, then
      progresses the transfer if the TX has been confirmed, otherwise it fails
      it, accepting the risk that the TX is confirmed later
- once the data of a transfer has been durably saved, calls
  `transfer.retrieved`, so the proxy can delete it while the transfer keeps
  counting towards the quota, or `transfer.delete` to also free its quota slot
  (e.g. for refused or fake transfers); for groups sharing an invoice (e.g.
  multisig cosigners) the first member retrieving the data shares it with the
  others by other means
- takes into account that, when the invoice lists more than one transport
  endpoint, the total number of transfers can exceed the quota, since each
  proxy enforces it independently (see 4.4.3); extra non-donation transfers
  can be refused, while a strict global limit requires listing a single
  transport endpoint
- should periodically verify, until the invoice expiration, that its
  reservations are still in place on all the transport endpoints (e.g.
  `transfer.list` succeeds and `invoice.check` does not return `unknown`),
  reserving the invoice again after a proxy data wipe; a reservation taken by
  someone else cannot be recovered, so that transport endpoint should not be
  relied upon

## Appendix A: end-to-end payload encryption

This appendix specifies the end-to-end encryption of the consignment, the media
attachments and the signed TX. It is a layer that rides on top of the transport
protocol: the two parties encrypt and decrypt, while the proxy only ever stores
and returns the resulting bytes and never needs any of the material below. It
is documented here (rather than left to each implementation) as a reference and
so that independent clients can reproduce it identically and interoperate.

### A.1 overview

Encrypting the consignment, the media attachments and the signed TX prevents
privacy loss in cases where a third party were to gain access to proxy data.

Encrypting lots of data (i.e. big consignments or media) could impose a
non-negligible performance penalty, so it makes sense to keep consignment and
media encryption optional. This caters to cases where resource usage or
performance matter more than privacy, or cases where plaintext data is mandated
due to external reasons.

### A.2 cypher

Cypher choice matters at different levels:
1. hardware acceleration
    - cyphers with dedicated hardware acceleration support (i.e. AES-NI/NEON)
      offer big performance improvements
    - cyphers with generic hardware acceleration support (i.e. SIMD/AVX/NEON)
      offer significant performance improvements
2. no_std / WASM support
    - dedicated hardware acceleration requires OS access, it is tricky when
      targeting rust no_std and unavailable when targeting WASM
    - generic hardware acceleration should be supported even in WASM (i.e.
      WASM-SIMD)
3. streaming support
    - cyphers that support streaming operation allow the parties to start
      data transfers right away and offer the recipient the ability to process
      the data as it's downloaded instead of having to wait for the full
      download to complete
    - there are cyphers with dedicated (e.g. AES-GCM) or generic (e.g.
      ChaCha20-Poly1305) hardware acceleration support that also support
      streaming operation
4. compatibility
    - the chosen solution needs to be compatible with other systems to allow
      interoperability between different products

Considerations:
- dedicated hardware acceleration is not of interest due to its lack of support
  in WASM
- XChaCha20-Poly1305 is streaming-friendly and supports generic hardware
  acceleration, which is available on major hardware architectures like x86
  (SIMD/AVX), ARM (NEON) and even WASM (WASM-SIMD)
- XChaCha20-Poly1305 is very fast even on mobile devices with no hardware
  acceleration, where it should be able to process a stream of up to a few
  hundred MB/s, which means it should never choke a network link
- the one-shot (X)ChaCha20-Poly1305 AEAD is a well-defined standard, should be
  available on every target platform (e.g. `chacha20poly1305` for, `x/crypto`
  for go, libsodium and its bindings for C/C++/Python/Swift/Java/Kotlin,
  `@noble/ciphers` and libsodium.js for JS/TS) and lets the caller supply the
  nonce
- there is, however, no cross-language standard for the chunking layer on top
  of the AEAD and therefore it must be specified by this document so it can be
  reimplemented identically on top of the portable one-shot AEAD on any
  platform
- XChaCha20-Poly1305 (the extended-nonce variant) is preferred over plain
  ChaCha20-Poly1305 because the protocol uses a deterministic, hash-derived
  nonce: the 24-byte nonce leaves ample room for a derived nonce, whereas plain
  ChaCha20-Poly1305's 12-byte nonce would be too small once a chunk counter is
  carved out, making derived-nonce collisions a real risk

XChaCha20-Poly1305 (one-shot `xchacha20poly1305` AEAD, with a caller-supplied
nonce) offers good performance, portability and the needed functionality. The
chunked-stream framing defined in A.4/A.5, built on top of the one-shot AEAD,
provides streaming operation while remaining portable and deterministic.

Allowing the user any choice of cypher or stream handling doesn't seem of
interest, as it would mainly reduce the security and interoperability
guarantees of good fixed choices, while also complicating the protocol, so
fixed choices seem the best approach.

Implementation note: libsodium's
`crypto_secretstream_xchacha20poly1305` was considered, since it's a
widely-ported alternative, but was rejected because it generates a random
header (nonce) at initialization with no API to supply a deterministic one.
This is incompatible with the deterministic-ciphertext requirement this design
relies on for idempotent POSTs and the proxy's "cannot change" checks. Defining
a minimal chunk framing over the portable one-shot AEAD keeps full control of
the nonce while remaining easily implementable on every target platform.
Compatibility with other systems (chunk size, nonce construction, tag handling)
must be verified against the explicit framing in A.4/A.5.

### A.3 key derivation

Both sender and recipient independently derive the same shared secret from the
respective pairs of "own X25519 secret key" + "counterpart X25519 public key"
via Diffie-Hellman (ECDH/X25519).

The X25519 keys are obtained from the Ed25519 keys (the pubkey shared in the
invoice is the Ed25519 public key) via the standard Curve25519 birational map:
- public key: the Ed25519 public key is a compressed Edwards point encoding the
  `y` coordinate; the X25519 public key is the Montgomery `u` coordinate; the
  relation is `u = (1 + y) / (1 - y) mod p`, `p = 2^255 - 19`, `y != 1` (RFC
  7748); `u` is encoded as a 32-byte little-endian value with the x-sign bit
  discarded (X25519 uses only `u`)
- secret key: the Ed25519 secret key is the 32-byte seed (what RFC 8032 calls
  the private key; note that libsodium's 64-byte Ed25519 secret key is instead
  the seed followed by the pubkey); the X25519 secret scalar is
  `clamp(SHA-512(seed)[0..32])`, where clamping clears the low 3 bits of the
  first byte, clears the high bit of the last byte and sets the second-highest
  bit of the last byte (standard Curve25519 clamping)

These are consistent: multiplying the basepoint by the clamped scalar yields
the same `u` as converting the corresponding Ed25519 public key, so the ECDH
between the two parties' converted keys produces a shared secret both can
compute.

The raw shared secret must not be used directly as an encryption key: an X25519
shared secret is high-entropy but not uniformly distributed, and using it
directly would also conflate the shared secret with the symmetric key. It is
therefore run through HKDF (RFC 5869) to produce a single uniform 32-byte key
used for the consignment, media and signed TX.

HKDF parameters (fixed by this specification):
- hash: SHA-256 (HKDF-SHA-256)
- IKM (input keying material): the 32-byte X25519 shared secret
- salt: empty (RFC 5869 default); the shared secret is already high-entropy and
  unique per key pair, so no extract-stage salt is needed
- info: the UTF-8 bytes `rgb-proxy-server/enc/v<N>`, where `<N>` is the
  encryption-format version (currently `1`, i.e. `rgb-proxy-server/enc/v1`)
- L (output length): 32 bytes (the XChaCha20-Poly1305 key length)

So the derivation is:

```
PRK = HKDF-Extract(salt = <empty>, IKM = shared_secret)
key = HKDF-Expand(PRK, info = "rgb-proxy-server/enc/v1", L = 32)
```

The `info` label provides two kinds of domain separation:
- protocol/context separation: the constant `rgb-proxy-server/enc` prefix
  ensures that, should the same X25519 key ever be used in another context, the
  derived keys are unrelated
- version separation: the `v<N>` suffix is bumped only when the encryption
  format changes incompatibly (e.g. a change to the nonce construction, chunk
  framing or cipher). A bump yields a fresh, unrelated key, preventing an old
  and a new ciphertext from ever sharing a (key, nonce) pair under the same
  shared secret. Versions that remain format-compatible keep the same `info`,
  and thus the same key, so they can still decrypt each other's data.

Notes:
- PRK (pseudorandom key) is the intermediate uniform key produced from the
  (non-uniform) ECDH shared secret
- `salt` and `info` are non-secret, fixed and identical on both sides; they are
  effectively part of the wire format and must match exactly, lest decryption
  fails
- the encryption-format version `<N>` is also carried as a header on the
  encrypted blob (see A.6) so the recipient knows which `info` label to use
- party identities are already bound by the shared secret (which depends on
  both key pairs), so they are not repeated in `salt`/`info`
- a single key is used for the consignment, media and signed TX; this is safe
  because the nonce base (last 19 bytes of each item's SHA-256, see A.5)
  makes the chance of two different plaintexts sharing a (key, nonce)
  negligible (~152-bit collision) and the inputs are not attacker-controlled
- a slow, password-based KDF (e.g. Scrypt) doesn't make sense here, as it's
  meant to securely extract entropy from low-entropy inputs (e.g. a human
  password) and is intentionally slow, which would only pose issues for typical
  operation in this context; HKDF is extremely fast and is explicitly designed
  to be used with high-entropy inputs like a Diffie-Hellman output

### A.4 chunking

The data is encrypted in fixed-size chunks, whose size needs to be shared. To
avoid the need to share the chunk size for each operation, a fixed plaintext
chunk size of 64 KiB is chosen. It should be large enough to contain small
messages in a single chunk and small enough to support streaming communication
without choking slower links. The size is binary (1 KiB = 1024 bytes), i.e.
exactly 65536 bytes, and is fixed by this specification so both parties split
the plaintext identically.

Each chunk is encrypted as an independent XChaCha20-Poly1305 one-shot AEAD
operation, producing a 16-byte authentication tag per chunk (so each ciphertext
chunk is its plaintext chunk length plus 16 bytes). The plaintext is split into
65536-byte chunks: every chunk except the last is exactly 65536 bytes and the
last chunk holds the remaining bytes (up to 65536). The last chunk is flagged
as final via its nonce (see A.5). Binding the chunk index and the final-chunk
flag into the per-chunk nonce prevents chunk reordering, duplication and
truncation.

### A.5 nonce

XChaCha20-Poly1305 uses a 192-bit (24-byte) nonce and it's fundamental that
it's never reused for the same key, lest an attacker that gains access to
multiple messages encrypted with the same key and nonce has a chance to recover
the original plaintext.

It's also necessary to be able to reconstruct the nonce deterministically based
on the message, as the APIs need to remain idempotent, which isn't possible if
the nonce changes (a "cannot change" error would be raised on POST). This is
the main reason XChaCha20-Poly1305 is used instead of plain ChaCha20-Poly1305:
its large nonce makes a deterministic, derived nonce safe.

Each 24-byte per-chunk nonce is built as the concatenation of:
- a 19-byte per-message base derived from the plaintext data (see below)
- a 4-byte big-endian chunk counter, starting at 0 and incremented per chunk
- a 1-byte final-chunk flag (0 for non-final chunks, 1 for the last chunk)

The 19-byte base is taken from the hash of the plaintext data, specifically its
last 19 bytes. The hash is the SHA-256 used elsewhere (consignment hash /
signed TX hash / media attachment digest); to obtain the base, hex-decode the
64-character hash string into its 32 raw bytes (which also validates the hex
string is valid) and take the last 19 of those raw bytes (do not slice the hex
string).

This guarantees that each encryption uses a unique base nonce, since each file
has a different hash, and that the same file being sent to the same
recipient(s) would result in the same bytes each time, since the base is unique
but deterministic. With a 152-bit base derived from a 256-bit hash, the chance
of two different plaintexts producing the same base under the same key is
negligible.

Notes:
- the chunk counter and final-chunk flag are part of the nonce we construct
  ourselves (see A.4); they are not added automatically by the AEAD, which is
  a plain one-shot primitive operating on a single chunk per call
- if two recipients in a batch operation use the same pubkey, given that the
  file is the same, the resulting encrypted files will be identical (same
  shared secret, same base nonce) so this does not give an attacker additional
  material to break the encryption
- the chunk counter is big-endian to match the STREAM BE32 construction this
  framing mirrors and conventional network byte order; endianness is a
  convention only and does not affect uniqueness or security

### A.6 caveats

Encryption updates need to be considered, so a versioning system is included:
every encrypted blob is prefixed with a single-byte encryption-format version
(currently `1`), and that same version is bound into the HKDF `info` label (see
A.3). The recipient reads the prefix to select the matching label and
decryption procedure. The version is bumped only on incompatible format changes
(nonce construction, chunk framing or cipher); such a bump rekeys the data and
prevents cross-version (key, nonce) reuse. The prefix needs no separate
authentication: tampering with it selects the wrong key, which makes AEAD
decryption of the first chunk fail.

The current proxy implementation doesn't allow streaming upload or download but
this can be added later (e.g. with new APIs) and it makes sense to design the
encryption support to include this use case from the start.

### A.7 example

This example walks through encrypting a 200 KiB (204800-byte) plaintext.

The sender derives the symmetric key from the shared secret (see A.3) and the
19-byte nonce base from the plaintext hash (see A.5). The plaintext is split
into 64 KiB chunks, giving 3 full chunks and an 8192-byte final chunk:

| chunk | plaintext range (bytes) | plaintext size | counter (4-byte BE) | final flag | ciphertext size (incl. 16-byte tag) |
|-------|-------------------------|----------------|---------------------|------------|-------------------------------------|
| 0 |      0 -  65536 | 65536 | `00 00 00 00` | `00` | 65552 |
| 1 |  65536 - 131072 | 65536 | `00 00 00 01` | `00` | 65552 |
| 2 | 131072 - 196608 | 65536 | `00 00 00 02` | `00` | 65552 |
| 3 | 196608 - 204800 |  8192 | `00 00 00 03` | `01` |  8208 |

Each chunk is encrypted with XChaCha20-Poly1305 under the shared key and a
nonce of `base (19 bytes) || counter (4 bytes) || final flag (1 byte)`,
appending the 16-byte tag. The whole blob is then prefixed with the single-byte
encryption-format version (see A.6):

```
[0x01]             1 byte    version prefix
[chunk 0 || tag]   65552 bytes
[chunk 1 || tag]   65552 bytes
[chunk 2 || tag]   65552 bytes
[chunk 3 || tag]    8208 bytes   (final chunk, nonce final flag = 0x01)
```

Total size: 1 + 3 * 65552 + 8208 = 204865 bytes, i.e. 65 bytes of overhead over
the 204800-byte plaintext: one 16-byte tag per chunk (4 * 16 = 64) plus the
1-byte version prefix.

To decrypt, the recipient reads the version prefix to select the matching
format and `info` label, derives the same key and nonce base, then decrypts the
fixed-size 65552-byte ciphertext chunks in order (counter 0, 1, 2, …, final
flag `00`), verifying each tag; the shorter final chunk that ends the blob is
decrypted with the final flag set to `01`. The final flag prevents truncation:
dropping the last chunk would leave a non-final chunk at the end, whose tag
would fail to verify as a final chunk.

### A.8 file types

The consignment, the media attachments and the signed TX are all encrypted with
the scheme defined in A.2 to A.6. The plaintext hashes for consignments
(`consignment_hash`) and TXs (`signed_tx_hash`) are sent alongside the files,
while media hashes are known from the asset metadata and are not transmitted
(the transmitted identifier is the derived `media_id`, see A.9).

The file types differ only in the following:

| file type | encryption | identifier |
|-----------|------------|------------|
| consignment | optional (per the recipient encryption preference) | `transfer_id` |
| media | optional (per the recipient encryption preference) | `transfer_id` + `media_id` |
| signed TX | mandatory | `transfer_id` |

Media requires additional, media-specific handling, detailed below.

### A.9 media

The plaintext media digest is known to both parties from the asset metadata. It
is used only locally, for nonce derivation (see A.5) and to verify the
decrypted media; it is never sent to the proxy.

Media is addressed by the transfer ID and an opaque per-media identifier
`media_id`. The transfer ID scopes the media to a transfer, the media ID
distinguishes the (possibly multiple) media attachments of a transfer.

`media_id` is NOT the plaintext digest: sending the plaintext digest would leak
which media is being transferred, because anyone observing the call (e.g. the
proxy) who has a candidate cleartext file could match its SHA-256 against it
and recognize the media even though its bytes are encrypted. Instead `media_id`
is derived from the shared secret so only the two parties can compute it:

```
Kmid     = HKDF-Expand(PRK, info = "rgb-proxy-server/enc/v1/media-id", L = 32)
media_id = hex(HMAC-SHA256(Kmid, media_digest))
```

where `PRK` is the extract output from A.3 and `media_digest` is the
hex-encoded SHA-256 of the plaintext media. Both parties know `media_digest`
and the shared secret, so both compute the same `media_id`; an observer with a
candidate cleartext can compute `media_digest` but, lacking the shared secret,
cannot compute `media_id`, so cannot recognize the media.

`media_id` is used for all media, both encrypted and cleartext. For cleartext
media the bytes are exposed anyway, so the identifier adds no content privacy,
but using `media_id` uniformly keeps every stored media strictly per-transfer
and avoids special-casing.

Notes:
- the recipient derives the decryption nonce from the plaintext `media_digest`
  (which it knows locally) and verifies the decrypted media against it
- because `media_id` is keyed by the shared secret, the same media sent to
  different recipients (or in different operations, since senders use fresh
  per-operation keys) gets a different `media_id`, so the proxy cannot
  correlate it across recipients or operations
- no cross-recipient de-duplication is possible (the same cleartext media
  yields a different `media_id` per recipient, hence a separate stored copy);
  this is intentional, as global de-duplication keyed by the plaintext digest
  would conflict with the per-reservation data retention policy: a shared blob
  could not be deleted when one reservation expires without breaking the others
  (see 4.6)

### A.10 key and seed lifecycle

Senders must generate a new key pair for each operation and recipients must
generate a new key pair for each invoice, since the invoice ID, the transfer ID
(see 4 introduction) and the witness seal blinding factor (see A.11) are
derived from them and must be unique. Fresh keys also prevent counterparts and
proxies from linking a party's operations or invoices through its keys (see
section 5) and limit the impact of a compromised key to a single operation or
invoice. As a result, each operation yields a different shared secret (and thus
different media IDs).

Keys should always be generated from good-quality random data and stored. Also,
deriving the encryption keys from a wallet seed may not be possible (e.g. in a
watch-only wallet).

Signing requires a Twisted Edwards curve (Ed25519) key while encryption
requires a Montgomery curve (X25519) key. A pair of Ed25519/X25519 secret keys
can be derived from a single 32-byte seed. These keys are related and the
corresponding X25519 pubkey can be extracted from the Ed25519 pubkey. Building
on this, the parties only need to generate a single seed, then derive and only
share their Ed25519 pubkey, which will be converted to its X25519 counterpart
when needed (i.e. to derive the shared secret). The pubkey shared in the
invoice and in proxy calls is therefore the Ed25519 pubkey.

The Ed25519 → X25519 conversion used to derive the shared secret is specified
in A.3. Implementations should use a vetted routine for it (e.g. libsodium's
`crypto_sign_ed25519_pk_to_curve25519` /
`crypto_sign_ed25519_sk_to_curve25519`, or equivalents such as `@noble/curves`
`edwardsToMontgomery*` or `curve25519-dalek` `to_montgomery`) rather than
re-implementing the field arithmetic.

Reusing key material derived from a single seed for both signing (Ed25519) and
key agreement (X25519) is a known technique but is cryptographically delicate;
it is acceptable via the vetted conversion above, and these keys must not be
used for any other purpose.

Only the seed needs to be stored. The two secret keys and their corresponding
pubkeys can be derived on-the-fly each time they're needed at a negligible
cost.

### A.11 seal blinding

For witness receives, the blinding factor of the seal assigning assets to the
recipient output is not chosen by the sender but derived from the shared secret,
so both parties compute the same value:

```
Kbld     = HKDF-Expand(PRK, info = "rgb-proxy-server/enc/v1/seal-blinding", L = 8)
blinding = u64_le(Kbld)
```

where `PRK` is the extract output from A.3 and `u64_le` interprets the 8 bytes
as an unsigned 64-bit little-endian integer, which is the format of RGB
blinding factors.

The sender uses `blinding` for the recipient witness seal. The recipient
derives the same value (using the sender pubkey returned by `consignment.get`)
and uses it, together with the script and the vout of the output, to identify
the output paying the invoice (see 6.4).

Notes:
- the shared secret is unique to the sender key pair of the operation and the
  invoice key pair, so the blinding factor is unique per transfer, even when
  the same address is reused across transfers
- the blinding factor is known only to the two parties, so a third party that
  knows the invoice (e.g. a public one) cannot recognize the recipient seal in
  a consignment it gets to see
- the sender cannot choose the blinding factor, so it cannot weaken the
  recipient privacy by choosing a bad (e.g. reused) one
- the recipient can verify the blinding factor, so a consignment using a
  different one does not pay the invoice and is refused
- the dedicated HKDF `info` label keeps the blinding factor unrelated to the
  encryption key and to the media IDs derived from the same shared secret
- blind receives are unaffected: the blinding factor is chosen by the recipient
  and embedded in the invoice concealed seal

## Appendix B: invoice interaction (recommended)

The recipient conveys to the sender two pieces of information needed by this
proposal: its Ed25519 pubkey and, optionally, its encryption preference for the
consignment and media. The recommended and interoperable way to do so is
through the invoice, described here. This interaction is not part of the proxy
protocol (the proxy never sees the invoice) but it is documented so clients can
converge on a common mechanism.

The invoice format is defined by the RGB invoice standard (outside this
protocol). It supports query parameters, which are already used, among others,
for transport endpoints (recipient proxy URL). The same mechanism carries the
recipient pubkey, using the `pk` query parameter, and the encryption
preference, using the `enc` query parameter. This remains compatible with old
clients that can still parse invoices even though they do not understand the
new extensions.

When creating an invoice, the recipient:
- generates a fresh key pair for the invoice (see Appendix A.10)
- stores them (the seed), associated with the invoice
- uses the invoice's `pk` query parameter to include the chosen Ed25519 pubkey
- sets the invoice expiration, which is mandatory and must be the same as the
  `expires_at` used to reserve the invoice on the recipient proxies, hence not
  further in the future than the lowest `max_expiry_secs` among them (minus
  some margin for clock skew)
- reserves the invoice on all the transport endpoints it lists via
  `invoice.prepare`, with the optionally chosen quota, before sharing the
  invoice; if a proxy refuses the reservation, the recipient either lowers the
  expiration so that all proxies accept it or removes that transport endpoint
  from the invoice
- uses the invoice's `enc` query parameter to optionally include its
  consignment and media encryption preference:
    - no `enc` query parameter (default) means encryption is mandatory for
      consignment and media; the recipient will refuse cleartext ones
    - `enc` set to `0` means encryption must not be used for consignment and
      media; the recipient will refuse encrypted ones
    - `enc` set to `1` means encryption may be used for consignment and media;
      the recipient will accept both encrypted and cleartext ones

When parsing an invoice, the sender:
- extracts the `pk` and `enc` query parameters
- if `pk` or the expiration is missing stops processing the invoice as invalid
- decodes and validates the pubkey in the `pk` query parameter
- stores the pubkey associated with the operation for encryption and ACK
  verification
- if `enc` is missing, encrypts the consignment and media (default)
- if `enc` is `0`, posts the consignment and media in cleartext, or fails if
  this is not acceptable
- if `enc` is `1`, can choose between encrypted or cleartext consignment and
  media, and should default to encrypted
- computes the invoice ID (see 4 introduction) and calls `invoice.check` to
  learn whether the invoice can accept a transfer

Notes:
- the `enc` value applies to the consignment and the media attachments but not
  to the signed TX, which is always encrypted, so a recipient must support
  encryption regardless of the `enc` value (in this context `enc` expresses a
  preference about the consignment and media, not a lack of encryption
  capability)
- the recipient uses a fresh key pair for each invoice, shared by all the
  transfers to that invoice, while the sender uses a fresh key pair for each
  operation (see 6.4)
- the sender can refuse to process an invoice that specifies an operational
  mode in which some guarantees are missing (i.e. cleartext consignment and
  media required) but, if it's acceptable, honoring the recipient's requested
  mode of operation is recommended for compatibility reasons
- the invoice is not a proxy-only object and can be used in other contexts,
  these recommendations are intended only for use with operations that rely on
  this proxy protocol for data exchange

## Appendix C: adaptive proof of work

This appendix specifies the proof of work the recipient proxy can require on
`consignment.post`. Unlike the other appendices it is part of the protocol,
since the proxy verifies it, but it is documented here for readability.

### C.1 overview

Invoices can be shared publicly, so anyone can create transfers for them and
fill their quota with fake ones (see 4.4.15 and section 5). The optional proxy
authentication cannot prevent this, since `consignment.post` must remain open
to any sender.

The proof of work puts a price on the volume of `consignment.post` calls. It
complements:
- the optional proxy authentication on `invoice.prepare`, which controls who
  can reserve invoices and quotas
- `transfer.delete`, which lets the recipient remove fake transfers and restore
  the quota
- the `consignment.post` signature, which prevents taking over a transfer ID

The difficulty is 0 during normal operation, so honest senders only pay for it
while an invoice or the proxy is under attack.

### C.2 puzzle

The sender must find a `pow_nonce` (1 to 64 printable ASCII characters, i.e.
bytes 0x20-0x7e) such that the hash:

```
SHA-256(transfer_id || pow_timestamp || pow_nonce)
```

has at least `d` leading zero bits, where `d` is the current difficulty for the
invoice and the input is the concatenation, encoded as UTF-8 bytes, of the
three fields, with no separators. Leading zero bits are counted on the 32-byte
digest, starting from the most significant bit of its first byte.

Notes:
- the `transfer_id` makes each solution valid for a single transfer, since a
  transfer ID can only be created once (and cannot be reused after being
  deleted)
- the puzzle does not include the uploaded file hash (`blob_hash`), so the
  sender can compute the proof of work before or while building the operation
  and a proof of work failure never requires rebuilding or re-signing the
  operation; the uploaded file is bound by the `consignment.post` signature
- `pow_timestamp` must be within 300 seconds of the proxy clock, which limits
  how many solutions can be computed in advance; clients can use `current_time`
  from `server.info` to compensate for clock skew
- both `pow_timestamp` and `pow_nonce` are chosen by the sender, the proxy only
  provides the difficulty
- the `pow_nonce` format is fixed so that both parties hash the same bytes
  (printable ASCII has a single UTF-8 encoding, with no normalization or
  escaping ambiguity) and the proxy can bound the input it hashes; 64
  characters leave ample search space (e.g. a decimal counter); a nonce with an
  invalid format is refused as invalid (`pow_nonce`) rather than as an invalid
  proof of work
- the difficulty is expressed in bits rather than bytes since each additional
  bit doubles the expected work, giving the adaptive difficulty a fine
  granularity (a byte would multiply it by 256)
- SHA-256 makes verification cost a single hash, so posts with bogus proofs of
  work cost the proxy nothing significant; it is also available on every
  platform and already used throughout this specification
- GPUs and other dedicated hardware compute SHA-256 much faster than the
  devices used by honest senders, so the proof of work prices scripted spam
  rather than well-equipped attackers; memory-hard functions (e.g. Argon2id)
  were considered, but they narrow the gap with GPUs by a small factor while
  their verification costs the proxy a full evaluation, which an attacker could
  abuse by posting bogus proofs of work at almost no cost; cheap to verify
  alternatives have also been considered (e.g. Equi-X) but their support is
  limited so interoperability would be a serious issue

### C.3 difficulty

The difficulty required for a `consignment.post` call is:

```
d = min(d_max, max(d_rate, d_global))
```

where:
- `d_max` is the configured maximum difficulty (`max_pow_difficulty` in
  `server.info`)
- `d_rate` is a per-invoice difficulty, based on the number of recent
  `consignment.post` calls for the invoice, counted with a decay over a time
  window `T` so that older calls weigh less
- `d_global` is a proxy-wide difficulty, based on the transfers recently
  created across all invoices (e.g. their number or the storage they use)

Each term is 0 while its load is below the configured threshold. The difficulty
is expressed as a number of leading zero bits and changes in steps of 1 bit.
It:
- rises instantly, as soon as the computed value is higher than the current one
- decreases only after the current value has been in effect for at least `H`,
  at which point it can drop to any computed value, including 0

Only `consignment.post` calls that create a transfer (i.e. that pass every
check, the proof of work included) count towards `d_rate` and `d_global`, while
rejected calls, idempotent re-posts and `invoice.check` calls don't. The
difficulty prices the creation of transfers, which is what fills invoice quotas
and proxy storage: a rejected call creates nothing and never paid a proof of
work (it fails before or at its verification), so counting it would let anyone
raise the difficulty for every honest sender at no cost, while a higher
difficulty would not make such calls any more expensive. Floods of rejected
calls are a generic request load that the proof of work cannot price, and are
handled by ordinary means (e.g. per client rate limiting and enforcing upload
size limits while receiving).

The rise and the hold time `H` apply to `d_rate` and `d_global` separately: each
term keeps its own current value and the time it took effect, since `d_global`
also changes with the calls for other invoices, and the required difficulty is
computed from the two terms in effect.

Notes:
- `d_rate` protects each invoice and keeps refilling a quota expensive after
  the recipient deletes fake transfers, since it depends on recent calls and
  not on how full the quota is
- no difficulty depends on how full the quota is: a nearly full quota can be
  legitimate (e.g. the recipient seldom deletes settled transfers), so honest
  senders only pay while there's an actual attack
- `d_global` protects the proxy against attacks spread across many invoices,
  each staying below the `d_rate` threshold; it applies to all invoices, so
  honest senders to invoices not under attack also pay while it's active, and
  should be enabled even on authenticated proxies, since authentication limits
  storage but not the availability of public invoices
- the smooth decrease comes from the decay over `T`, while `H` prevents the
  difficulty from oscillating around a threshold
- there is no grace period after a rise: a sender whose proof of work is no
  longer sufficient just computes a new one and retries; since each additional
  bit doubles the work, being overtaken by successive rises costs less than
  about twice the final difficulty
- setting `max_pow_difficulty` to 0 disables the proof of work

The recommended `max_pow_difficulty` is 24, which should take roughly 1 second
with native code on a mid-range phone, 3 to 8 seconds in a mobile browser and
about half a second on a single desktop core; since the number of attempts is
geometrically distributed, about 5% of the proofs take three times as long or
more. Operators targeting different clients can derive a cap as the base-2
logarithm of the acceptable wait times the number of attempts per second of the
slowest targeted client. For example, targeting an expected wait of 5 seconds
in a mobile browser computing about 3.4 million attempts per second gives
log2(5 × 3.4 × 10^6) = log2(17 × 10^6) ≈ 24, the recommended value. Clients can
refuse to compute proofs of work above their own limits, in which case they
cannot create transfers on that proxy.

### C.4 wire behavior

- `server.info` exposes `max_pow_difficulty`
- `invoice.check` returns the current difficulty (`pow_difficulty`) for each
  invoice
- `consignment.post` always requires `pow_timestamp` and `pow_nonce`; when the
  current difficulty is 0 any value is accepted, so the sender can always run
  the same code (with a difficulty of 0 the first nonce it tries is valid)
- the proxy only verifies the proof of work if the current difficulty is
  greater than 0, and after all the other checks (see 4.4.5), so an identical
  re-post is never subject to it and no proof of work is required to learn
  that the invoice cannot accept the transfer
- if the proof of work does not satisfy the current difficulty or its
  `pow_timestamp` is outside the allowed window, the proxy returns an "invalid
  proof of work" error including the current difficulty; the sender computes a
  new proof of work (with a fresh `pow_timestamp`) and retries

### C.5 behavior over time

```
d_max ┤        ┌──────────────┐
      │       ╱│ deletes free │╲
      │      ╱ │ quota, rate  │ ╲  decays over T (decreases gated by H)
      │     ╱  │ keeps d high │  ╲
    0 ┼────╯   └──────────────┘   ╲──────
      quiet   attack (instant rise)  attack stops   quiet
```

1. quiet: all terms are below their thresholds, the difficulty is 0
2. attack: the calls exceed the threshold, `d_rate` rises instantly
3. the recipient deletes fake transfers: the quota is restored, but `d_rate`
   stays high, so each refill costs about `2^d_max` attempts
4. the attack stops: the difficulty decays over `T` back to 0
5. an attack spread across many invoices: `d_global` rises for all invoices

### C.6 attacker strategies

| strategy | answered by | result |
|---|---|---|
| keep refilling a quota the recipient keeps restoring | `d_rate` | each call costs about `2^d_max` attempts, so the attacker needs continuous computing power |
| attack, pause for `T`, resume | `T` / decay | each cycle gets the calls below the threshold for free, plus the rise back up |
| fill the quota slowly, below the `d_rate` threshold | none (accepted) | takes a long time and is treated as low-rate spam that the recipient cleans up |
| fill the quota once while the recipient is offline | `d_rate` during the fill | not prevented: the invoice stays full until the recipient deletes the fake transfers |
| spread across many invoices on one proxy | `d_global` | prevented at the proxy level, at the cost of honest senders to other invoices |
| spread across several proxies | none | each proxy is independent, but an invoice lists only a few transport endpoints |

### C.7 tunables

| tunable | set by | effect |
|---|---|---|
| hash function (SHA-256), puzzle format and difficulty unit (bits) | specification | interoperability |
| `pow_timestamp` window | specification (300 s) | shorter limits precomputation but causes more clock skew failures |
| `d_max` | operator (advertised via `server.info`, recommended 24) | worst case cost for honest senders and attacker cost per call; 0 disables the proof of work |
| `d_rate` threshold and rise | operator | when and how fast `d_rate` rises; too low makes honest senders to popular invoices pay, too high gives attackers more free calls |
| `T` and decay | operator | how smoothly the difficulty decreases after an attack and how expensive it is to pause and resume an attack |
| `H` | operator | minimum time between decreases, prevents oscillation |
| `d_global` threshold and rise | operator | protects the proxy; lower thresholds make honest senders to other invoices pay sooner |
| `quota` (up to `max_quota`) | recipient | a larger quota takes more calls to fill, at the cost of more storage and cleanup |

Suggested operator defaults are left to the implementation, which should
document them.

### C.8 deployment

- public proxy: proof of work enabled, `d_global` enabled
- private authenticated proxy hosting public invoices: proof of work enabled,
  `d_global` enabled, since authentication does not protect public invoices
- private authenticated proxy hosting private invoices only: the proof of work
  can be disabled (`max_pow_difficulty` set to 0), since a third party cannot
  target an invoice it doesn't know

### C.9 limits

- the proof of work makes spam at scale expensive, but cannot stop a
  determined attacker from keeping a single invoice full: its cost is roughly
  the recipient deletion rate times `2^d_max` attempts
- it provides no protection while the recipient is offline, as fake transfers
  are not deleted
- the proof of work only prices successful transfer creations: floods of
  rejected `consignment.post` calls cost the attacker no proof of work and must
  be handled by generic request rate limiting
- honest senders only pay during attacks, up to about `2^d_max` attempts; since
  each attempt is a single SHA-256, clients can estimate the worst case from
  `d_max` alone
- attackers with dedicated hardware (e.g. GPUs) compute proofs of work much
  faster than honest senders, so the protection is mostly against scripted
  spam rather than well-equipped attackers
- puzzles that are both memory-hard and cheap to verify (e.g. Equi-X, used by
  Tor) could narrow the gap with dedicated hardware, should mature
  implementations become available for the relevant platforms
